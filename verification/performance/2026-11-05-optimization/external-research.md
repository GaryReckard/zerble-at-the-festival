# Optimizing Zerble’s Performance on Older iPads

Zerble’s rich festival scene (instanced crowds, colorful campsites, day/night lighting, rolling terrain) can overwhelm an older iPad’s GPU and CPU.  In practice, even highly optimized mobile scenes can run at only ~15 fps on five-year-old phones when rendering millions of triangles.  On iOS Safari, giant textures or overly high resolutions often trigger crashes or throttling. We must therefore slash workload while preserving “perceived richness.”  Below are several promising techniques, ranging from established best practices to more speculative ideas. Each entry includes the targeted bottleneck, references, a falsifiable experiment, trade-offs, implementation difficulty, and how to measure real gains (avoiding confusion with simply removing content).

- **Lower Rendering Resolution (Pixel Ratio).**  Reducing the canvas resolution directly cuts GPU workload. For example, if the game uses a retina scale (devicePixelRatio > 1), capping it at 1 or 2 on mobile can significantly boost FPS.  This attacks the “draw as many pixels as possible” cost on a slow GPU. (*Source:* Common mobile-WebGL advice indicates that high DPR multiplies fragment work, even though we lack a specific citation. However, Apple’s engineers often test on older devices; N. Arnfield advises testing textures on older phones as “a texture that looks fine on a current laptop may behave differently on an older phone”.)  
  - *Experiment:* Render the same scene on desktop (via iPad Simulator) and measure frame time at DPR=1 versus DPR=2 using `renderer.setPixelRatio`.  If the lower DPR cuts frame time significantly without obvious blur, the technique is useful.  
  - *Trade-offs:* Visual sharpness is reduced.  Distant details become blurrier on Retina displays. This is acceptable if readability remains.  
  - *Complexity/Risk:* **Low**. Changing pixel ratio is trivial; it has no long-term risks. It affects all scenes uniformly.  
  - *Measure Success:* Compare GPU/fragment timing counters or raw FPS with and without change, keeping all scene content identical. Confirm that the same draw-calls are executed (so only resolution changed). A true efficiency gain will show lower GPU load at the same content count.  

- **Instanced LOD for Crowds and Foliage.**  Use Multiple Levels of Detail (LOD) with InstancedMesh.  Even though crowds and trees are already instanced, they may all use full-detail geometry. By creating, say, two or three versions of each model at decreasing polygon counts, and swapping instances based on camera distance, we cut vertex/fragment work for distant objects.  The Chinese Three.js case study demonstrates exactly this: one InstancedMesh per LOD level, and dropping instance count in-view.   This targets the rendering bottleneck (triangle throughput).  
  - *Source:* The technique is well-known: _“use Level of Detail so that when far from camera, show low-poly versions”_.  The case study shows instanced LOD in Three.js yielding playable 15 fps on old phones.  
  - *Experiment:* Create simplified LOD meshes (e.g. half and quarter detail) for representative crowd/tree models. Instrument a dense crowd scene in the desktop lab: enable LOD switches at various distances while measuring total triangle count and FPS. A successful test will show lower triangle counts and higher FPS with LOD, and visually little change to the scene. Compare camera screenshots to ensure distant crowd still looks full.  
  - *Trade-offs:* More memory (storing multiple meshes), plus pop-in/artifacts if LOD thresholds are abrupt.  Careful blending or crossfading might be needed. Visual fidelity at distance is reduced (some fine detail lost), but if art style is forgiving it may be unnoticeable.  
  - *Complexity/Risk:* **Moderate**. Requires producing and loading extra models or decimating existing ones, and coding LOD selection.  Instancing code already exists, which simplifies group rendering.  Risk is moderate: wrong LOD logic could cause distracting popping or incorrect collisions.  
  - *Measure Success:* Compare *per-frame draw counts and triangle counts* with and without LOD. Ensure the scene object count remains the same (we’re just using cheaper meshes, not culling objects). If GPU/CPU time drops while crowd remains visually similar, that’s a real gain. Also track if input latency changes (shouldn’t).  

- **Texture Compression (KTX2 / Basis).**  Convert all diffuse/normal maps to GPU-compressed formats (KTX2 with Basis).  Compressed textures stay in GPU memory and upload faster.  This reduces memory bandwidth and load times, key for iPad GPUs with limited VRAM.  For example, KTX2 images remain compressed on the GPU, using “less memory” and making the first frame load sooner.  Pixelfogg’s guide also notes GPU-ready Basis textures “drastically reduce memory footprint” and mentions LOD through lower-resolution textures for distant objects.  
  - *Source:* Khronos and developer guides highlight KTX2/Basis benefits.  (“Texture Compression and LOD: We aggressively utilize formats like KTX2 and Basis Universal…reducing memory footprint.”)  Niall Arnfield’s write-up shows KTX2 files often upload faster and use less memory than PNGs.  
  - *Experiment:* Convert a set of festival textures (e.g. tent fabrics, crowd clothing) to KTX2/Basis. Measure GPU memory usage (Three.js’s `renderer.info.memory.textures`) and loading times. On desktop, run the scene with original textures vs. compressed ones. If compressed textures consume much less GPU memory (as on glTF.report) and frame times drop, it’s effective. Also check visual quality: Basis can introduce artifacts.  
  - *Trade-offs:* Possible minor loss of texture fidelity (blockiness or color shifts). Initial conversion adds build complexity (require KTX2 tools). On some very old hardware, Basis/ASTC might not be supported, requiring fallbacks (though most iPads support ASTC or ETC).  
  - *Complexity/Risk:* **Moderate**. Requires changing the asset pipeline (or using Three.js’s KTX2Loader). Low runtime risk. If a device doesn’t support the format, textures might not appear (testing needed).  
  - *Measure Success:* Monitor `renderer.info.memory.textures` and GPU memory. Also instrument frame times. Ensure the *number of draw calls and geometry* are unchanged, so any gain comes from lower memory/bandwidth cost, not content removal.  

- **Merge Static Geometry & Reduce Draw Calls.**  Many small meshes (vendor booths, fences, props) each trigger a draw call. Merging same-material meshes or using InstancedMesh for any repeating props cuts overhead.  Three.js best practices advise merging or instancing to “generate rest of system with one model”.  Our existing geometry-merging experiment failed on one test, but we can try finer-grained merges: e.g. group static objects by material, or use InstancedMesh for repeated decorations. This directly addresses draw-call and CPU-side overhead.  
  - *Source:* GenAnywhere’s Medium guide lists “Reuse & Merge” as a key tip: merge geometries with same material, or use InstancedMesh for repeating objects. This “doubles render efficiency for large scenes” without adding draw calls.  
  - *Experiment:* Identify a set of static objects (e.g. campsite decorations) with identical materials. Programmatically merge their BufferGeometries or put them into an InstancedMesh. In the lab, compare draw-call counts (`renderer.info.render.calls`) with the original. Measure FPS: if fewer calls yield higher FPS at same scene complexity, it works. (As a control, ensure the actual content hasn’t changed – i.e., count of items remains constant.)  
  - *Trade-offs:* Merged geometry cannot be culled individually; if far off-screen, the entire merged mesh still exists (though bounding-box culling may handle it). Also, merged colliders would need updating. We must disable or manage frustum culling on originals accordingly. The benefit is huge if there were thousands of tiny draws; downside is reduced flexibility (can’t toggle parts easily).  
  - *Complexity/Risk:* **Moderate**. Three.js has `BufferGeometryUtils.mergeBufferGeometries`, but results must fit GPU limits (max index count). Very large merges may hit WebGL limits. Using InstancedMesh for non-dynamic repeated assets is straightforward. The main risk is correctness (materials must match exactly). Since our broad merge failed before, trying smaller groups is safer.  
  - *Measure Success:* Track draw calls and CPU time for traversal (Three.js stats). Confirm that the reduction in draw calls corresponds with performance gain. Ensure visual content remains the same (just batched).  

- **Simplify Shaders / Baked Lighting.**  Replace any heavy real-time lighting with cheaper techniques. For example, use unlit or MatCap shaders for crowd and static props instead of full Phong/Standard material. Pixelfogg notes “writing custom, unlit GLSL shaders that ‘fake’ lighting via MatCaps … achieve stunning aesthetics at a fraction of the computational cost”.  Also consider baking static lighting into textures (lightmaps) so the GPU does less per-pixel work. This cuts fragment-shader cost.  
  - *Source:* Pixelfogg’s mobile guide directly advocates custom unlit shaders: “Standard materials…are heavy… By writing custom, unlit shaders…we achieve stunning aesthetics at a fraction of the cost.” Three.js examples and games often use lightmaps or low-poly stylized lighting for performance.  
  - *Experiment:* In the test scene, swap one object’s material for a simple unlit shader or MatCap. Measure GPU fragment time (via `renderer.info.render.frame`). Do the same with a small bake on a vendor box. If the frame time significantly drops while appearance is still acceptable (i.e. audience doesn’t notice loss of dynamic shadows or specular), it’s beneficial.  
  - *Trade-offs:* Loss of realistic lighting. The scene may look flatter or less dynamic. We must ensure artistic style allows it. Baked lighting requires additional art work. However, for a colorful stylized festival, this might be acceptable.  
  - *Complexity/Risk:* **Moderate to High**. Writing custom shaders or generating lightmaps is extra work. There’s some risk in visual mismatch (shadows may “pop”). But it’s an established technique in performance-critical games.  
  - *Measure Success:* Use GPU timing queries or Three.js performance monitors to compare fragment cost with original shading. Confirm no geometry count change. Visually inspect to ensure no unwanted flicker.  

- **World-Generation Chunking / Web Workers.**  The synchronous stalls during procedural generation are a CPU-side bottleneck. Offload heavy math (terrain, object placement) to Web Workers or break it into smaller tasks.  As CoreJSC explains, moving heavy computation to a Web Worker moves it off the main thread so UI (including rendering) stays responsive. If workers aren’t used, one should “yield to the event loop” between chunks (e.g. `await new Promise(r=>setTimeout(r,0))`) so the browser can paint frames.  
  - *Source:* This is a general web-dev best practice from CoreJSC: “the only approach that keeps the UI fully responsive… is a Web Worker”. Even without workers, explicitly yielding between chunks prevents long frame freezes.  
  - *Experiment:* Identify a worst-case generation function (e.g. building a new map chunk). Run it on desktop and use `console.time()` or profiler to measure how long it blocks the main thread. Then refactor it to run in a Worker or as small async pieces. Measure the max blocked time (should drop from hundreds of ms to sub-50ms chunks). Also ensure visible frame rate no longer stutters. If unloading a chunk no longer freezes the app, it’s a win.  
  - *Trade-offs:* More complex code and debugging (Workers can’t access Three.js scene directly, so you must message data back and forth). If not careful, partial updates could lead to visible construction artifacts (e.g. popping geometry in). UI latency is improved but total load time might slightly increase due to overhead.  
  - *Complexity/Risk:* **High**. Refactoring generation into a worker or async loop is significant. Risk includes bugs in threaded code and race conditions. However, it does not change gameplay directly and is reversible.  
  - *Measure Success:* Use performance profiling to verify that long frame delays are eliminated. For example, Chrome’s timeline or Three.js stats should show no single task >50ms during loading. The *total* time to build all content might be slightly higher, but UI remains smooth. Ensure that with and without change, the end result has the same content.  

- **Optimize Per-Frame Logic (Avoid Expensive Math).**  Audit the game’s update loop for costly operations. On iOS/Safari, some math functions are surprisingly slow: one example found Math.abs took up to 308 ms when called repeatedly per frame. Replacing such calls with cheaper operations (e.g. `ceil`, bitwise tricks, or lookups) can reclaim CPU time. This attack CPU-bound bottlenecks.  
  - *Source:* A Three.js forum post notes that calling `Math.abs` multiple times per frame on Safari consumed ~308 ms (versus ~111 ms on Chrome). The remedy was using `Math.ceil` or reducing calls.  
  - *Experiment:* Profile the rendering loop on Safari (with devtools) and look for any functions consuming large percentages (e.g. heavy trigonometry or absolute values). Replace a suspect call (like `Math.abs`) with a cheaper alternative or precalculated value. Measure frame time or CPU time via `performance.now()`. If the loop becomes faster, the change is effective.  
  - *Trade-offs:* Very minor. In rare cases, minor numerical differences (rounding vs absolute) might occur. Generally safe.  
  - *Complexity/Risk:* **Low to Moderate**. It’s a code audit task. Risk is minimal, but one must be careful not to break correctness. It mainly affects old devices (the post cites Safari specifically).  
  - *Measure Success:* Compare frame times or loop duration with profiler open. Confirm that the count of iterations hasn’t changed and that only CPU cost changed.  

- **Physics Simplification.**  Although not yet confirmed heavy, Rapier physics could be a bottleneck if many bodies are simulated. Ensure only essential collisions are calculated each frame. For example, disable collision for far-away crowds, or reduce the physics simulation rate (e.g. 30 Hz instead of 60 Hz). Use simpler colliders (spheres or capsules) for characters instead of mesh colliders. This cuts CPU and possibly a bit of GPU work (if debug drawing).  
  - *Source:* No direct source in our search, but general game dev practice (physics engines allow stepping at lower rates to save CPU).  
  - *Experiment:* If profiling shows physics time is significant, try halving the physics update frequency or switching some colliders to simple shapes. Measure physics loop time and overall frame time. If the game still behaves acceptably, it helps.  
  - *Trade-offs:* Collisions may be less accurate. Crowds might not move perfectly on uneven terrain. Must preserve “collision correctness,” so any shortcut should not break the game (e.g. main cart collisions must stay correct).  
  - *Complexity/Risk:* **Moderate.** Tuning a physics engine risks subtle bugs (e.g. carts clipping terrain). However, physics is on a separate subsystem, so changes are isolated.  
  - *Measure Success:* Compare total time spent in `rapier.step()` or similar. Ensure no visible physics glitches. Verify that collision outcomes (e.g. cart hitting obstacle) remain the same.  

- **Adaptive Content Culling.**  Finally, consider not rendering non-essential details. For example, use frustum culling aggressively (Three.js does this by default), shorten camera far-plane so extreme distant objects are never drawn, or skip animating off-screen characters. You could even “billboard” distant crowd clusters as 2D sprites, though that’s more complex. These approaches reduce work by reducing visible content. They partially reduce *content*, so measurement must ensure we don’t just cheat by hiding things.  
  - *Source:* The Chinese case (and Three.js docs) implies using frustum culling and LOD. [6] specifically mentions disabling default frustum culling on source objects when doing instanced culling, which suggests careful culling is needed. Three.js automatically culls by bounding volume.  
  - *Experiment:* For example, shorten the camera’s far plane to cut draw distance and see if frame time rises without noticeable scene emptiness. Or group far crowds into a single billboard. Compare FPS but also note how much content is removed. If the scene’s visual fullness is largely unaffected, it can be a success.  
  - *Trade-offs:* This explicitly removes or hides content, which directly changes the game experience (some distant vendors or crowd will vanish). Must be done subtly (e.g. skybox covers horizon, pop-ins outside view).  
  - *Complexity/Risk:* **Variable.** Simple culling is low risk; advanced billboarding/impostors is high risk and effort. Risk is in accidentally hiding something the player expects to see.  
  - *Measure Success:* Frame time will improve, but this is partly “cheating” by content loss. To verify efficiency, measure the ratio of frames saved per object culled. Ideally, test by comparing frame time versus object count, to show the system can handle nominal scene without hidden content.  

## Top Proposed Experiments (Ranked)

Based on expected impact and feasibility, here are the **five highest-priority experiments**:

1. **Lower Render Resolution (pixel ratio):** Capping DPR to 1 or 2 on Safari can double/triple FPS on retina iPads with essentially *no development effort*, at the cost of softness. This is a well-known quick win for WebGL on mobile. *(Impact: High; Risk: Low)*  
2. **Instanced LOD for Crowds/Trees:** Adding distance-based LOD to existing instanced objects targets the largest GPU load (millions of triangles). If done carefully, it should yield substantial gains with minimal perceived loss. *(Impact: High; Risk: Moderate)*  
3. **Texture Compression (KTX2/Basis):** Converting bulky festival textures to GPU-ready compressed formats will cut memory use and bandwidth, easing Safari’s limitations. This is fairly straightforward and tested (e.g. via glTF tooling). *(Impact: Medium; Risk: Low)*  
4. **Off-Thread/Chunked Generation:** Refactoring world/chunk construction into a Web Worker or an async chunked process will eliminate the giant frame hitches seen on iPad. This doesn’t increase FPS, but it makes playback smooth. It’s more complex to implement, so we rank it after easier wins. *(Impact: Medium; Risk: High)*  
5. **Simpler Shaders / Baked Lighting:** Replacing dynamic lighting with unlit/MatCap shaders or lightmaps for static scene parts can yield big GPU savings. This requires art-side work but avoids heavy per-pixel math. *(Impact: Medium; Risk: Moderate)*  

Each of these experiments should be measured **carefully**.  For instance, when testing LOD or culling changes, ensure you compare frame time while *keeping the same number of base objects in the scene* – the goal is reduced work, not removed content. Always profile CPU and GPU time (via devtools or Three.js stats) rather than relying on FPS alone, and try to keep visual richness constant when measuring.  Combining these techniques should allow Zerble to run far more smoothly on older iPads without fundamentally sacrificing the festival’s liveliness.

**Sources:** Official docs and developer write-ups show that instancing, LOD, texture compression, and task scheduling are critical for mobile WebGL. For example, an open-source Three.js city demo uses instanced draw, frustum culling, and LOD to hit ~15 fps on a midrange phone. Mobile WebGL guides emphasize KTX2/Basis textures and unlit shaders. We also use forum wisdom (e.g. limiting iOS texture sizes, avoiding slow math operations, and chunking heavy work) to shape these proposals.
