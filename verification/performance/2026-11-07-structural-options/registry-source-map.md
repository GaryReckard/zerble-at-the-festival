# Registry spatial maintenance source map

TL/DR: The current implementation already updates changed grid cells incrementally, but it discovers those changes by scanning every resident entry on every accepted game frame. The substantial redesign is explicit spatial mutation ownership or a small declared mover set, plus event-driven radius/list maintenance, rather than introducing incremental insertion for the first time. No runtime code was changed and no tests, browser sessions, servers or benchmarks were run for this source investigation.

## What the profile establishes

The supplied sampling report attributes 2,374.773 ms of self samples to `rebuildSpatialIndex` out of 59,840.666 ms total sampled time, approximately 3.97% of that report's total. The report explicitly distinguishes sampling attribution from elapsed main-loop timers, so this is neither a per-frame duration nor a measured potential FPS gain (`high-route-attribution.json:2-3`, `:29-34`). Removing the function's entire sampled cost is an optimistic ceiling for that capture, not a defensible forecast, because replacement maintenance and query costs remain.

## Maintenance and callers

- There is no invalidation flag and no lazy query-triggered rebuild. `add()` immediately inserts footprint/collider membership, records the indexed position/category and grows conservative radius maxima (`src/registry.js:89-122`); `remove()` removes using the last indexed position, including move-then-remove before frame synchronization, and immediately removes oversized-list membership (`src/registry.js:125-145`). Chunk unload delegates to indexed entry removal (`src/registry.js:157-160`; `src/chunks.js:610`).
- The live game unconditionally calls `rebuildSpatialIndex()` after the vehicles slot and before adult steering, within the frame body (`src/main.js:1463-1472`). The people workshop also calls it before adults/children (`src/people/workshop.js:29-41`), and the hoop workshop calls it before adults/roaming (`src/people/hoop/workshop.js:97-103`). These are the production-source call sites found by `rg -n rebuildSpatialIndex src`.
- The misleadingly named rebuild walks **all** entries, checks cell or membership-class changes, removes/inserts only changed memberships, reconstructs the oversized-footprint array, recomputes both maximum radii and refreshes recorded positions (`src/registry.js:305-334`). It therefore avoids most static grid writes while retaining an O(resident entries) discovery pass.
- Radius changes within the same footprint class do not require reinsertion because entries are live references. Radius maxima and exact callbacks still need the new values; changing footprint between zero, small-grid and oversized classes does require membership changes (`src/registry.js:314-330`, `:341-350`). Radius maxima grow immediately on add and physical publication, then shrink to exact maxima on the next full scan; removal does not recompute them (`src/registry.js:107-120`, `:125-145`, `:237-239`, `:332-333`). Keeping an old larger maximum is safe for membership but widens candidate walks, so an event-driven design needs a deliberate shrink policy.

## Static scenery, ordinary movers and physical movers

The registry contract has no explicit static/dynamic classification: the ordinary entry schema contains position, footprint, optional collider/attractor and chunk ownership, while the constructor builds shared footprint and collider grids for all of them (`src/registry.js:49-77`, `:80-88`). Representative static scenery is forest trees allocated at fixed world coordinates with footprint/collider/chunk ownership (`src/forests.js:924-937`), and lake envelopes allocated with fixed center and bounding radius without chunk ownership (`src/lakes.js:580-594`). Lake cleanup removes its recorded IDs itself, except adopted physical chairs (`src/lakes.js:916-919`). These examples establish ownership differences, not an exhaustive immutable-entry inventory or measured static-to-moving ratio.

Verified ordinary mutation writers include:

- OneWheel riders register position/footprint/collider entries, then mutate their positions directly every update (`src/oneWheels.js:85-94`, `:112-121`).
- Nut Wagon registers three collider/footprint entries and `sync()` transforms each entry's live position from its local offset (`src/nutWagon.js:85-90`, `:122-126`).
- Hoopers retain registry identities while inactive and switch footprints between zero and an avoidance radius while moving their positions (`src/people/hoopers.js:48-53`, `:221-228`). Their controller runs in the roaming slot (`src/people/hoopers.js:31`), which is after the live game's spatial barrier (`src/main.js:1469`, `:1506`). A redesign must decide whether to preserve that existing next-barrier grid-membership timing; publishing immediately can change what later same-frame queries observe.

Physical props already use an immediate mutation API: `publishPhysical()` validates a complete publication, mutates live geometry and calls `_syncPhysicalEntry()` (`src/registry.js:197-213`). That helper changes affected cell memberships, maintains the oversized list in ID order and grows maxima (`src/registry.js:216-239`). This is a useful implementation precedent, but it is tied to bounded physical enrollment and canonical placement geometry, not a general static/dynamic registry partition (`src/registry.js:163-182`, `:260-270`). Generation queries skip enrolled props at their live poses and additionally scan their canonical geometries, so moving a physical prop must not free its original worldgen reservation (`src/registry.js:263-270`).

## Semantics the redesign must preserve

1. **Same-pass worldgen visibility.** New entries enter grids immediately so placement guards can see earlier additions during the same construction pass (`src/registry.js:102-106`). `closestBuilding()` uses exact edge distance after broadphase and excludes tree kind by default (`src/registry.js:376-403`). The real-code guard test exists specifically to protect same-seed placement from boolean changes (`bin/test-registry-grid:6-23`).
2. **Candidate order, not only membership.** Both registry grids sort each cell by entry ID (`src/registry.js:57-62`), and `SpatialGrid` traverses Z cells then X cells, followed by array order (`src/spatialGrid.js:77-86`). Ordered insertion/removal preserves that sequence when movers re-enter cells (`src/spatialGrid.js:40-71`). Footprint queries append oversized entries after grid candidates (`src/registry.js:341-345`). Two separate static/dynamic grids cannot simply concatenate results without changing the sequence; a single grid with explicit updates avoids this new merge obligation.
3. **Collision consequences depend on ordering.** The game appends registry candidates before people providers and passes that list to the ordered resolver (`src/main.js:1806-1820`); the resolver processes in order, applies contact response, and returns from the first qualifying impact (`src/collisionContacts.js:18-43`, `:48-74`). Keeping the same hit set alone is insufficient.
4. **Avoidance arithmetic also follows callback order.** Crowd steering accumulates weighted X/Z repulsion and strength across footprint callbacks (`src/crowd.js:2928-2949`). Changing visitation order can change floating-point accumulation even when membership matches.
5. **Broadphase is X/Z and conservative.** The cell size is 8 m and footprint radii >=16 m use the separate oversized list (`src/registry.js:18-19`, `:107-115`). Queries add the largest corresponding radius and callers perform exact tests (`src/registry.js:336-350`); height-aware collision eligibility remains downstream (`src/collisionContacts.js:31-37`).
6. **Canonical physical geometry and ownership remain separate.** Generation queries deliberately include original placement geometry instead of physical live poses (`src/registry.js:263-270`); ownership transfer preserves insertion order in chunk buckets (`src/registry.js:242-255`). An index redesign must not conflate moving geometry with chunk ownership or physical enrollment.

## Cheap proof surfaces for a planned redesign

These are proposed next probes, not executed results:

- Run `node bin/test-registry-maintenance` without `--bench`. Its real Registry fixture already checks 1,500 mutation/unload states against full-rebuild **candidate membership and order**, move-before-remove, zero writes for within-cell motion and empty-cell retention (`bin/test-registry-maintenance:20-55`). Adapt its mutation cases to the new explicit API while retaining a baseline oracle. Add max-radius removal/shrink and repeated 15.9/16 boundary transitions because the planned design removes the scan that currently refreshes those facts (`src/registry.js:309-333`).
- Run `node bin/test-registry-grid`, `node bin/test-registry-indexes` and `node bin/test-registry-physical`. The first imports real code for placement truthiness/minimum-edge-distance parity (`bin/test-registry-grid:15-25`); index tests include live position/attractor replacement and unload/reload (`bin/test-registry-indexes:205-253`); physical tests exercise 600 immediate publications across cell/class/radius changes, canonical-versus-live queries and unaffected-candidate ordering (`bin/test-registry-physical:160-191`).
- Add a bounded Node probe importing the real Registry and SpatialGrid, with a counted `entries.values()` iterator and counted insert/remove calls. Replay the current maintenance test's deterministic event stream through baseline and proposed paths and require identical ordered candidates. Count scanned entries, explicit dirty updates, cell transitions and maximum-radius refreshes before timing anything. The existing optional benchmark only compares today's full scan against an older clear/reinsert implementation, so its result would not establish the new redesign's improvement (`bin/test-registry-maintenance:57-67`).
- Before deleting discovery, inventory entry-position/footprint/collider writes using source searches and add a debug-only shadow audit that compares declared dirty IDs with observed changes at the existing frame barrier. The verified direct writers above establish why add/remove hooks alone cannot safely eliminate scanning (`src/oneWheels.js:121`; `src/nutWagon.js:126`; `src/people/hoopers.js:48-53`). Measure this audit only as correctness instrumentation, then remove or disable it during cost capture.
- For real-route evidence, the later experiment should count resident entries, declared movers, dirty updates, radius/list maintenance and ordered-query parity alongside elapsed maintenance time. The present profile contains sampled self-cost only (`high-route-attribution.json:2-3`, `:29-34`), while the existing source tests use synthetic fixtures (`bin/test-registry-maintenance:8`, `:58`). Neither establishes the route's actual mover ratio or a device FPS gain.

## Planning recommendation

Prefer one shared ordered grid per query type with explicit ordinary spatial publication, a small declared mover set where direct mutation must remain, and event-driven oversized/max-radius maintenance. Keep the existing frame barrier and same-pass add/remove behavior. Separate static/dynamic **ownership** is the useful architectural change; physically splitting the grids introduces ordering work that the current shared grid already avoids (`src/registry.js:57-62`; `src/spatialGrid.js:77-86`). The acceptance gate should prove complete mutation coverage and ordered query equivalence before the real-route experiment establishes whether saved discovery cost outweighs replacement bookkeeping.
