## Audit's Position

### Context: what already happened here

Deliberation `001-initial-plan` ran on 2026-08-26 (same day the artifacts were authored). All three personas returned **Proceed with mitigations**, and the Mediator's synthesis (`deliberations/001-initial-plan/results.md`, Final Recommendation) set an explicit precondition:

> "do not begin renderer integration until the OpenSpec artifacts encode the v2-only gate, immutable descriptor boundary, centralized owner lookup, shared streaming deadline, versioned pending work, and exact tier budgets."

This audit's central finding is that **none of those amendments were applied**. `proposal.md`, `design.md`, `spec.md`, and `tasks.md` are unchanged relative to the versions the council critiqued (every `results.md` line citation still resolves against the current files, e.g. `design.md` D6's flag-only gating and D1's mutable `loaded` reference). The plan as written still walks into the Critical and High findings the council already accepted. Everything below re-verifies those against the actual code (cite-or-cut) and adds five new findings the first round missed.

### Priority Sequence

1. **Fold results.md Change Group 1 into the four plan artifacts before anything else.** The v2-only gate, `isLoaded(cx, cz)` predicate, exported owner-cell helper, single world-owned streaming deadline, versioned pending snapshots, immutable-descriptor copies, road elevation contract, bounds-recompute rule, and the `worldgen-layout` baseline clarification must appear in `design.md`/`spec.md`/`tasks.md` text, not only in the deliberation folder. Verified against code below; each one is real.
2. **Add the completion-signal caveat to D4/task 3.2** (new finding V7): `loaded.has` == "fully built" is true today only because `_generateWorldgen` is synchronous; two code comments already announce intra-chunk splitting as planned. Bind handoff to a named contract, not an implementation accident.
3. **Re-spec the promotion gate against a measured baseline** (new finding V9): the absolute per-tier draw budgets the synthesis adopted may already be exceeded by the shipped game per `perf.js`'s own B0 profiling comment, which would make the gate unsatisfiable and the feature permanently unpromotable as specified.
4. **Specify per-cell horizon planning** rather than one monolithic `queryRegion` over the full radius (sharpens the accepted double-budget finding with cold-cost evidence from git).
5. Then proceed with the implementation order the synthesis already established (harness + baselines → cheapest three batches → gates).

### Vulnerabilities Found

- **[V1 — KILLER] The accepted council synthesis was never written back into the plan artifacts**: `results.md` (Final Recommendation; Change Group 1, Task 1) conditions implementation on artifact amendments. The current artifacts still lack all of them: `design.md` D6 gates enablement on `?farField=1` alone; D1 passes "a read-only `chunkManager.loaded` reference"; D3 grants the horizon "the tier's 3/4/5ms chunk budget" as a second wall; `tasks.md` 2.2 still says only "narrower and lower"; `spec.md` has no v2-gate scenario and no bounds-refresh requirement; `proposal.md` still declares "Modified Capabilities: None" despite the accepted `worldgen-layout` clarification (baseline conflict verified below, V11). This project's plans are executed by cheaper models following `tasks.md` literally; as written, `tasks.md` re-derives every hazard the council already found and accepted mitigations for. — Severity: **Critical**
- **[V2] `?worldgen=0&farField=1` renders a false v2 horizon over the v1 world**: `src/perf.js:68-74` — `USE_WORLDGEN_V2` still honors `?worldgen=0` as a live escape hatch, and `src/chunks.js:395-419` branches to the legacy theme path when it's off. `design.md` D6 and `tasks.md` 1.2 resolve enablement from `?farField` only. In that combination the horizon draws v2 hearts, plans, and arterials that correspond to nothing the chunk system will ever build, and loaded v1 chunk keys will hide unrelated v2 proxies. Effective enablement must be `farFieldRequested && USE_WORLDGEN_V2`, with a legacy no-op test. (Re-verified from the prior round; still unaddressed in artifacts.) — Severity: **Critical**
- **[V3] "Read-only" inputs are mutable shared caches**: `festivalPlan` returns the array instance held in `_seamedCache` (`src/worldgen/festival.js:719,824-830`), and the roads layer's cached per-cell polyline arrays are explicitly documented as shared (`src/worldgen/roads.js:247-251`). `ChunkManager.loaded` is a live mutable `Map` (`src/chunks.js:306`). One in-place sort, clip, or annotation in `farField.js` silently mutates the generator's cached truth for later real-chunk builds — a determinism break with zero RNG calls touched, invisible to any RNG-draw-count test. The plan must mandate defensive copies into FarField-owned records plus pre/post input hashing in `bin/test-far-field`, and replace the `loaded` reference with an `isLoaded(cx, cz)` predicate. — Severity: **High**
- **[V4] The streaming budget is double-counted and the cold call is indivisible — and git proves cold road queries are expensive**: `ChunkManager.update` can spend the entire `PERF.chunkBudgetMs` before returning (`src/chunks.js:349-352`; 3ms on low, `src/perf.js:90`), then `design.md` D3 gives the horizon "the same" wall — up to ~6ms of streaming before render on the weakest tier. Worse, D3's slicing plan can't slice `queryRegion` itself: a 520m horizon means a ~1km² bounds query, and commit `ce0be6c` records that cold arterial computation was a measured multi-second stall before per-cell caching ("cold stall ~13s→~1-2s"). One world-owned deadline (chunks first, FarField gets the remainder), per-cell incremental planning (the road cache is already per-200m-cell, so iterate cells instead of one monolithic bounds call), versioned pending snapshots, and a measured max-indivisible-step gate are all required in the artifact text. — Severity: **High**
- **[V5] Handoff ownership is specified by duplication, not one source of truth**: the half-open cluster-ownership rule exists only as a local closure (`src/worldgen/placement.js:31`), the chunk key format is private to chunks.js (`src/chunks.js:644-646`), and player-cell derivation uses `Math.round` (center-anchored cells, `src/chunks.js:314-315`) where a naive implementer reaches for `Math.floor` (corner-anchored). `farField.js` re-implementing any of the three gives a horizon whose proxies hide the wrong cell — correct at the spawn hub, wrong at negative coordinates or across a rename. Export one pure owner-cell helper from `placement.js` and add `ChunkManager.isLoaded(cx, cz)`; lock negative-boundary fixtures in `bin/test-far-field`. — Severity: **High**
- **[V6] Rewritten pools can be frustum-culled on stale bounds**: `design.md` D2 requires `needsUpdate` flags on matrix/color writes but says nothing about `InstancedMesh.boundingSphere` or the road `BufferGeometry`'s bounds. Three.js r160 (pinned via importmap, `.claude/rules/no-build.md`) computes an InstancedMesh bounding sphere once and never recomputes it on matrix writes; an atomic rewrite that moves active instances hundreds of metres leaves bounds describing the previous snapshot, so a valid new horizon vanishes at specific camera angles. Recompute bounds after every committed rewrite (or disable frustum culling on the six batches and account for the cost), and assert enclosure after a second distant rebuild in the focused test. — Severity: **High**
- **[V7] NEW — "`loaded.has` means fully built" is an implementation accident that the code already plans to break**: D1's handoff correctness rests on "`loaded.has(ownerKey)` changes only after real generation completes." That holds today because `_generateWorldgen` runs synchronously start-to-finish (`src/chunks.js:485-540`) before `this.loaded.set(...)` (`src/chunks.js:412`). But `src/perf.js:89` already says "Dense single chunks are split separately," and `src/chunks.js:1361-1364` marks builders staying synchronous only "until they are explicitly split at a safe internal boundary." The moment that queued work lands, `loaded.has` fires before the stage exists and the proxy dissolves into briefly-empty ground — a pop the whole feature exists to remove. The spec must name the contract it depends on ("proxy hides only after the owning chunk's cluster props exist") so a future chunk-splitting change is forced to provide a real completion signal, and `openspec/specs/world-streaming/spec.md` ("Chunk lifecycle on an 80m grid") should carry that clarification when this change applies. — Severity: **Medium** (latent High)
- **[V8] Boot-path construction and reduced-motion ordering**: `buildWorld` runs at module evaluation, before the title tap (`src/main.js:422`), while `A11y.init()` — the point where persisted/OS `prefers-reduced-motion` is resolved — runs later (`src/main.js:611`; `src/a11y.js:21-28`). A FarField constructed inside `buildWorld` that plans synchronously lengthens first paint on the longest boot chain; one that caches `A11y.reducedMotion` at construction reads the default `false`. Initial ownership must snap (no envelope), initial planning must be measured separately, and reduced motion must be read live per handoff. The title-tap → `Sound.init()` adjacency (`src/main.js:648-651`) is untouched by the plan and must stay that way. — Severity: **Medium**
- **[V9] NEW — the synthesis's absolute-budget promotion gate may be unsatisfiable on day one**: `results.md` (Change Group 3, Task 4; Conflicts Resolved, last row) requires the enabled representative view to hold the absolute tier budgets (low 80 draws / 150k tris, etc.). But `src/perf.js:40-42` records B0 profiling of the shipped game at "~3.7k median / 9.2k peak draws vs a 400 budget." If the flag-off baseline already exceeds the absolute budget on a tier, the gate can never pass regardless of how well FarField behaves, and task 5.5's promotion decision is dead on arrival while appearing to be a fair test. Capture the disabled baseline first (Change Group 1 already schedules this); if it's over budget, re-key the gate to marginal delta + no-regression + explicit Gary sign-off, and say so in `tasks.md` 5.4/5.5 rather than discovering it at gate time. — Severity: **Medium**
- **[V10] NEW — hub-sandbox far-field mode goes stale on FESTIVAL_TUNING epoch bumps**: the plan's primary iteration surface (`design.md` D7, `tasks.md` 4.1) lives in `hub-sandbox.html`, whose live tuning panel rebuilds the hub on slider release, and worldgen memoization is gated on (seed, epoch) — an epoch bump clears `_planCache`/`_seamedCache` wholesale (`src/worldgen/festival.js:722-724`). A FarField snapshot keyed only on player cell keeps rendering the pre-bump plan against the rebuilt post-bump hub: misaligned proxies in exactly the surface meant to prove alignment. Task 4.1 must include epoch-aware invalidation (rebuild the FarField snapshot on the same trigger that rebuilds the hub). — Severity: **Medium**
- **[V11] Baseline spec conflict is confirmed and the proposal still denies it**: `openspec/specs/worldgen-layout/spec.md` ("Persistent lifecycle (no chunkKey)") says every worldgen feature carries `lifecycle: 'persistent'` and no `chunkKey`, while `openspec/specs/festival-composition/spec.md` ("Cluster-center ownership filter") and the actual consumption path chunk-key every festival cluster (`src/chunks.js:574,802,1039,…`). FarField handoff binds to the chunk-owned interpretation. `proposal.md` "Modified Capabilities: None" leaves the new capability depending on a baseline that contradicts itself; the accepted narrow `worldgen-layout` clarification must ship as a spec delta in this change. — Severity: **Medium**
- **[V12] NEW — road-underlay risk class is material/draw-order, not classic z-fighting; spec the right test**: the human-corrected failure on this exact surface was a `depthWrite:false` material built at module eval rendering invisibly under the player-centered ground (commit `db4e0ef5`, Gary, 2026-06-07 — also the source of the "create materials lazily/at construction" rule). Ground is flat at world y=0 (`src/rng.js:82-84`; `src/world.js:396-401`), the real road sits at y=0.06 (`src/chunks.js:989`), and with camera near=0.5 (`src/main.js:170`) the projected depth separation of horizontal decals from a low chase cam grows with distance/height ratio, so a ≥3cm lift is depth-safe at 300-520m. The genuine hazards are: an unspecified elevation (tasks 2.2's bare "lower"), `depthWrite`/render-order mistakes of the `db4e0ef5` class, and top-down sandbox captures (where separation IS only Δy). Spec the elevation as an explicit constant in (0, 0.06), require `depthWrite:true` opaque, construction-time material creation, and both grazing-angle and top-down captures. — Severity: **Medium** (was High as vaguely spec'd; concretizing the numbers is the fix)
- **[V13] NEW — task 1.3 over-scopes the importmap rule to map-sandbox**: `bin/check-importmaps` requires every `src/*.js` in the three 'full' pages only; `map-sandbox.html` is role `'wg'` (worldgen + rng, `bin/check-importmaps:30-36,60`). Adding `farField` to map-sandbox's `wg` array is inert (the extras check only validates `worldgen/*` tokens, `bin/check-importmaps:66-70`), so task 1.3 as written neither breaks nor is enforced on the fourth page. Reword to "the three full pages (`mods` arrays), enforced by `bin/check-importmaps`" so an implementer doesn't burn time hunting a fourth array or mistrust the green check. — Severity: **Low**
- **[V14] NEW — the horizon accelerates the `_seamedCache` cliff**: the plan cache clears in full at >4000 entries (`src/worldgen/festival.js:829`). A 520m horizon query touches roughly 6-7× the heart area per crossing that 80m chunk placement does, reaching the cliff sooner on long travel; the clear then makes the next real chunk generation recompute its neighborhood plans cold inside the chunk budget. Pre-existing behavior, amplified. Cheap mitigation: note it in the long-travel test (task 5.4's plateau capture will surface it as a periodic spike if it matters). — Severity: **Low**
