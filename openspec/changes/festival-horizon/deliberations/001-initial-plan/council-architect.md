## Architect's Position

### Priority Sequence

1. **Amend the ownership and scheduling contracts before renderer work.** Export one pure half-open owner-cell helper from `src/worldgen/placement.js`, make FarField use it, and define whether `world.js` coordinates one aggregate streaming deadline or FarField owns a separate measured budget. The current plan promises both exact placement ownership and work "under the same" 3/4/5ms wall, but neither is yet represented by a shared API (`design.md:97-105`; `src/worldgen/placement.js:24-35`; `src/chunks.js:348-353,644-646`).
2. **Move the isolated harness shell ahead of the visual implementation.** Scaffold the hub-sandbox mode, deterministic fixture, fake/read-only loaded-chunk source, resource counters, and explicit FarField teardown before building the six batches. This follows the project's harness-first rule and gives the owner-key, handoff, disposal, and pool tests a real integration surface instead of leaving Task 4.1 until after world integration (`AGENTS.md:23-28`; `tasks.md:13-47`).
3. **Implement the fixed owner-scoped renderer behind the default-off flag.** Build one FarField root with fixed-capacity instance and road buffers, stable identities and tie-breakers, explicit update flags, and a single idempotent `dispose()`. Candidate retention must be independent of whether an owner chunk is currently loaded so an unload can reveal the already-planned proxy without a rebuild (`spec.md:98-102,115-126`).
4. **Integrate through `world.js`, not through `ChunkManager` or the registry.** `world.js` should construct and update the peer after authoritative chunks, expose it to local debug through a getter or the existing `buildWorld` return shape, and pass live state through narrow dependencies. FarField must never import builders, register entities, or participate in `disposeChunkByKey` (`design.md:47-57`; `src/world.js:47-89`; `src/chunks.js:591-608`).
5. **Promote only after lifecycle truth is proven in the full game.** The sandbox proves composition and owner transitions; the game must prove title/start boot, phased chunk completion, unload/reappearance, live reduced-motion changes, resource plateaus, and clean low/mid/high shader compilation. Only then should the default and ROADMAP state change (`tasks.md:55-83`).

### Structural Risks Identified

-   **Owner-key drift is the sharpest boundary risk.** The handoff is correct only if the proxy and real builder derive the exact same owner. Today the half-open predicate is a local closure inside `placeChunkProps`, while the loaded-map key formatter is private to `chunks.js` (`src/worldgen/placement.js:24-35`; `src/chunks.js:644-646`). Reimplementing `floor((x + 40) / 80)` and the `"cx,cz"` key in `farField.js` would create a second source of truth, especially at `-40`, `40`, negative coordinates, and exact corners. Task 1.1 should require an exported pure `ownerChunkForPoint` helper from `placement.js`, boundary fixtures on both signs, and an assertion that its key addresses the same `ChunkManager.loaded` entry. `ChunkManager` remains authoritative; the helper only centralizes identity.

-   **The peer systems do not currently share a streaming deadline.** `ChunkManager.update` creates its own `performance.now()` start and returns no elapsed time or remaining budget (`src/chunks.js:348-362`). If FarField starts another 3/4/5ms timer after it, the combined frame can spend nearly twice the stated wall even though each subsystem passes locally. The design must choose one falsifiable contract before Task 3.3: either `world.js` owns a deadline that chunks consume first and FarField uses only the remainder, or the horizon gets a separately named, smaller `farFieldBudgetMs` and acceptance measures the aggregate. The spec cannot continue calling two independent timers the "existing" streaming budget (`spec.md:128-132`). Chunk generation must retain priority because it owns gameplay correctness.

-   **The canonical lifecycle prose is internally inconsistent, so FarField must bind to the correct authority explicitly.** The live festival contract says the chunk containing a descriptor center builds the whole cluster (`openspec/specs/festival-composition/spec.md:109-120`), and the implementation chunk-keys those real resources (`src/worldgen/placement.js:1-7`; `src/chunks.js:1288-1306,1452`). However, `worldgen-layout` still says every worldgen feature is persistent and carries no `chunkKey` (`openspec/specs/worldgen-layout/spec.md:161-170`). Horizon handoff must ignore `queryPoint.lifecycle`; its truth is descriptor-center ownership plus `ChunkManager.loaded`. The change documentation should reconcile that stale canonical statement or narrowly state that it applies only to the render-agnostic query feature tuple, not the chunk-built festival clusters. Otherwise the proposal's claim that all existing capability contracts remain intact is misleading (`proposal.md:38-42`).

-   **Reappearance requires loaded-state-independent snapshots.** The specification correctly promises that an unloaded chunk reveals an already-planned proxy without rebuilding (`spec.md:98-102`), but nearest-capacity selection could accidentally omit currently loaded candidates to save slots. That optimization is forbidden. The snapshot must select solely from stable descriptor identity, tier radius, distance, and deterministic tie-breakers, then store the owner key and apply loaded state only to its visibility target. Stable identity should include the descriptor's `clusterSeed` plus semantic subpart so atomic buffer rewrites cannot transfer a fade envelope to another proxy.

-   **Resource sharing and ownership need precise language.** The proposal says the horizon follows `userData.shared` disposal patterns (`proposal.md:67-75`), while the design says every geometry and material is FarField-instance-owned and disposed by `FarField.dispose()` (`design.md:77-80`). Those are different lifetime models. The clean structure is an owner root that chunk and lake disposal never traverse, with resources allocated once per FarField instance and disposed explicitly once. `userData.shared = true` is only appropriate if a resource actually has module-global lifetime beyond that instance; using it as a generic pooling label would obscure ownership and can cause sandbox rebuild leaks. The test should call `dispose()` twice and verify scene detachment plus exactly-once GPU disposal without touching chunk or lake resources (`src/chunks.js:585-604`).

-   **Reduced motion must be read live, not captured during world construction.** `buildWorld` currently runs before `A11y.init()` (`src/main.js:413-425,605-612`), and the setting can change without reload (`src/a11y.js:18-47`). FarField therefore cannot cache a constructor-time boolean. Its handoff update needs a live getter or per-frame value, while an initial pre-render snapshot should snap directly to chunk ownership. This preserves immediate Settings behavior without moving `A11y.init()` into the title/start or audio chain.

-   **The proposed module boundaries otherwise align with the architecture.** A render-only peer owned by `world.js` is preferable to expanding `ChunkManager`: it owns no registry, collision, crowd, audio, or builder side effects, while `ChunkManager.loaded` changes only after a complete group has entered the scene (`src/chunks.js:383-413`). The six global batches, opaque proxy-only dither, no shadows/lights, fixed buffers, and explicit disposal match the render and lifecycle constraints (`design.md:59-80,102-120`). The new module is correctly included in the cache-buster task for all four HTML pages, matching the no-build rule (`tasks.md:9-11`; `.claude/rules/no-build.md:26-50`).

### Verdict

-   **Verdict**: Proceed with mitigations
-   **Key Concern**: The plan currently duplicates the real chunk-owner rule and claims a shared streaming budget without a shared owner-key or deadline API, so a locally correct FarField could still hand off the wrong cluster or double the frame's generation wall.
-   **Recommendation**: Apply the owner-helper, aggregate-budget, harness-order, live-reduced-motion, and explicit-resource-ownership amendments before game integration. With those seams closed, the bounded default-off render peer is structurally consistent with Zerble's world, registry, disposal, determinism, and no-build architecture.
