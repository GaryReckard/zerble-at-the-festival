## Findings

- [P1][high] src/crowd.js:2267 - The new unsafe-exit refusal corrupts an urgent rider's state because arrival still proceeds
  - Trigger: An urgent rider reaches the destination radius below 2 m/s while the physics cart is airborne or more than 40% immersed. The added guard returns false with the seat still reserved. `src/quests/runtime.js:207-208` ignores that result and calls `sendToPotty`, which writes `state = 'idle'` without releasing the seat (`src/crowd.js:2283-2285`). The engine already removed the request and incremented completed before the event, and runtime still pays and records the delivery (`src/quests/engine.js:119-122`, `src/quests/runtime.js:210-217`). Ordinary rides also receive premature completion, but the urgent variant additionally produces an idle person who still owns a cart seat.
  - Repro: With a riding NPC holding a seat, `grounded=false`, a stationary cart at the urgent destination, and a bathroom service refusing a claim, call `runtime.update(0.1)`. Actual probe output: `{"state":"idle","stillHasSeat":true,"rewards":15,"completed":1,"active":0}`.
  - Delta qualification: Ignoring a failed terrain landing was already a defect at the baseline. The new guard adds this failure to airborne/submerged exits even for riders without terrain bindings, where the old `_exitRide` would have released the seat. Main already contains transactional arrival preparation and a seated-person guard in `sendToPotty`; their absence from this branch is not itself a new deletion in the reviewed delta.
  - Fix: Preserve main's preflight/commit arrival contract when integrating. Keep the request and ride hold while a safe exit is unavailable, and invoke potty behavior, rewards, log writes and completion callbacks only after successful disembarkation. Retain the seated-person guard as defense in depth. Add an urgent unsafe-arrival regression that checks seat ownership and zero rewards until a subsequent safe landing.
  - Duplicate-of: Existing main transactional-arrival fix; this is its interaction with the new guard, not an independent request to redesign arrival.

- [P2][high] src/quests/runtime.js:175 - Run shutdown clears a monk quest without releasing the party's quest hold
  - Trigger: End a run while a monk party has an active shared request. New calls at `src/main.js:2072` and `src/main.js:2110` invoke `stop()`. `clear()` releases only solo holds (`src/quests/runtime.js:177`); the cancelled event deletes the party owner from the map at line 193 but has no corresponding party cleanup at lines 231-236. `monks.questHold` stays true even though no quest exists, suppressing ordinary timed departure (`src/monks.js:125`). An eventual dry tank or lost seat can still end the ride, so this is not an unconditional permanent seat leak.
  - Repro: Offer a party request whose owner has `questHold=true`, register that owner in `runtime.parties`, and call `runtime.stop()`. Actual probe output: `{"questHold":true,"active":0,"partyOwners":0,"enabled":false}`. The fake party's `leave()` clears its hold and re-enters `runtime.cancel`, matching the live callback shape at `src/main.js:917-918`, but is never called.
  - Delta qualification: Audit 001 identified the dormant `clear()` omission. This delta introduces production callers through `stop()`, making that known omission reachable at run end.
  - Fix: Release party-owned quest holds during reset cancellation through an explicit owner operation. If choosing `leave()`, retain the existing remove-before-callback order so reentrant cancellation remains harmless. Disable new offers before publishing shutdown events. Cover stop with a party owner, reentrant cancellation and a repeated stop call.
  - Duplicate-of: Audit 001's previously dormant clear/monk-hold omission, newly activated by shutdown wiring.

- [P2][high] src/crowd.js:2269 - The new 45-second delivery cooldown does not gate hailing or hail boarding
  - Trigger: Deliver an ordinary rider, allow the 2.6-second cheer to end, and move the cart at least 10 m from that person while staying within hailing range. The next hail attempt may select the same rider because `forEachHailCandidate` at lines 2198-2208 ignores `disinterestedUntil`. Stopping within 14 m then calls `hailBoard` at lines 2236-2243, which also ignores the deadline, so the person can immediately take another ride despite the new cooldown.
  - Repro: Run those actual source-extracted methods with actor time 104, an idle delivered person whose deadline is 145, and the cart stopped 12 m away. Actual probe output: `{"chosen":["delivered"],"boarded":true,"state":"boarding","remainingDisinterest":41}`.
  - Delta qualification: Immediate reboarding existed before this patch. This finding concerns the newly introduced 45-second guarantee, which only affects the ordinary proximity trigger (`src/crowd.js:1201`, `:1221`) while the primary quest pickup route bypasses it. Task 12.3 explicitly claims delivered riders wait 45 seconds.
  - Fix: Exclude people whose disinterest deadline exceeds actor time when choosing hailers, and check the deadline again in `hailBoard`. Add a regression covering rejection during the cooldown and eligibility after expiry.
  - Duplicate-of: Audit 001 immediate-reboarding defect, incompletely addressed by the new cooldown.

## Checks and integration notes

- No changed seeded RNG call, hash input, salt or procedural generation stream was found in the assigned delta. Changed quest picking consumes the already unseeded quest random source; it does not alter chunk, forest or lake generation.
- Hail reservations now count against ordinary and party offers at `src/quests/runtime.js:61` and `:86`, while a boarding hailer carries its existing plan at lines 52-57. The forced debug path intentionally bypasses hail reservations.
- The capture flags stop the runtime before board callbacks or ticks at `src/main.js:928`; disabled update and offer gates prevent subsequent quest searches and offers. The vehicle test added a once-only stop assertion, but its fake stop cannot detect party ownership failures.
- Actual person hit registration remains active for hailers: the exemption changes proximity dodge and honk scatter, while `src/crowd.js:2878-2889` still emits their colliders and `:2907-2921` still changes a struck person to fleeing. No claim of real-GPU approach safety follows from this static check.
- Main's stronger activity-claim/seat checks in `walkerInfo`, `hailWave`, `hailBoard`, and `sendToPotty` must survive integration. Their absence predates this delta and is not reported as a newly introduced regression. The current filter's surface-binding presence check at `src/crowd.js:2206` also does not establish matching surfaces; this is an incomplete prior eligibility fix rather than a new regression.
- The supplied runtime tests exercise hailing, cap reservation, low-priority toast forwarding and solo stop, but do not exercise actual crowd safety refusals or party stop. The focused probes above cover those missing ownership edges without claiming browser verification.
