# Build the eyes and the ruler before fixing the festival

> **Status:** <!--STATUS:LINE-->in progress · 2/38 tasks (5%)<!--/STATUS:LINE-->
>
> _Before we redesign how the festival lays itself out (that's the follow-up
> change, `festival-zone-grammar`), this change builds the tools to SEE layout
> problems and MEASURE whether they're fixed — so nobody has to find bugs by
> driving around the world hoping to spot them._

## TL;DR

Two rounds of playtesting found the new procedural festival "a jumbled mess" —
food trucks clipping into vendor rows, porta potties in random spots. Every fix
attempt so far was verified by eyeballing single locations, because no tool can
see the whole arrangement or check it against rules. This change builds that
tooling: a **linter** that checks every festival hub against the layout rules
(nothing overlapping, stages properly spaced, booths facing the road…), a **3D
hub viewer** that shows one complete festival hub on a single page, a way to
**capture what the game actually built** as data, and a hotkey so Gary's
playtest observations arrive as exact coordinates instead of descriptions. The
actual layout fix comes next, in `festival-zone-grammar`, measured against this
change's baseline.

## The Problem

The game world is generated by two cooperating layers: a *planner*
(`festival.js`) that decides "a food court goes about here," and *builders*
(`chunks.js`) that construct the actual trucks, tents, and stages. The planner
thinks in simple circles; the builders produce bigger, oriented shapes — and
nothing checks the two against each other. That's why things clip.

Worse, no existing tool can even *see* the problem. The 2D map sandbox draws
the planner's circles (which look fine). The entity sandbox shows one model at a
time (each looks fine). The determinism self-test proves the world is
*reproducible*, not that it's *good*. The only detector for "this arrangement
is wrong" has been Gary, driving around, writing down what he saw — the
slowest, most expensive feedback loop in the project.

## Proposed Fix

Build the verification surface first (the project's own doctrine), then fix the
layout in the follow-up change:

- **Capture built truth.** A debug call (`__dbg.dumpRegistry`) plus a
  one-command script (`bin/layout-snapshot`) save everything the game actually
  constructed — every truck, booth, and stage position — as a data file. This
  becomes the ground truth the linter checks and the safety net proving
  refactors didn't change the world.
- **A layout linter.** Executable rules — no overlaps, clear dancefloors,
  booths straddling and facing roads, stages spaced apart, spawn framed by the
  arch with the stage ahead — checked across many world-seeds at once. Every
  violation reports exact coordinates with links to see it in 2D, in 3D, and in
  the running game. Pre-fix violation counts get recorded as the **baseline**
  the grammar change must drive down.
- **A hub viewer** (`hub-sandbox.html`). One page that builds ONE complete
  festival hub — through the exact same code the game uses — with an orbit
  camera and live tuning sliders. This is where layout iteration happens in
  seconds, and where Gary-facing screenshots come from.
- **One shared constants module** (`FESTIVAL_TUNING`). The ~34 scattered layout
  numbers (ring sizes, row spacing, clearances) move into one file both the
  planner and the builders read — the prerequisite for the grammar change and
  for the sliders.
- **Playtest markers.** A hotkey that drops a pin (seed + position + heading)
  when Gary sees something wrong mid-drive, so feedback arrives teleportable.
- **A seed gallery.** A contact-sheet of many world-seeds at once, because one
  good-looking seed proves nothing about the rest.

The technical "how" — including determinism safeguards — is in
[design.md](design.md).

## Key Decisions

- **Harness before feature** — the grammar rewrite is gated on this change; its
  linter rules ARE the festival's layout spec, written as executable checks.
- **THE PIVOT (deliberation 001):** the first draft also planned to split every
  builder into a pure "layout function" now. The council's Adversary proved
  that's the repo's riskiest refactor class for a *secondary* benefit — the
  captured registry is already the exact truth. The split is deferred into
  `festival-zone-grammar` (where those builders get rewritten anyway), with its
  full design handed forward (design D-C′). This collapsed the
  must-not-change-anything window from ~10 commits to ~2.
- **Built layouts are tier-dependent today** (a real discovery: the crowd system
  draws from the same random stream with a per-tier pool size) — so all captures
  and the baseline pin one perf tier.
- **Sequencing across changes:** the v2 change's pending H.2 fix moves a
  determinism hash this change freezes against, so it lands first; and the
  "make v2 the default" flip moves to AFTER the grammar fix — the old plan
  would have shipped the jumble to real players.
- **Vocabulary:** captured world-data files are "layout snapshots," never
  "goldens" (the goldens are the two determinism hashes — keeping the terms
  apart on purpose).

## Risks & Watch-outs

- **Determinism** is the big one even after the pivot: the constants hoist
  touches code whose random-draw order produces existing worlds. Every such
  commit is gated on an empty snapshot diff + unchanged goldens + a draw-count
  canary that catches even invisible changes.
- **The hub viewer could lie** — it runs game code outside the game. Mitigated
  by registering lakes first, never omitting the crowd, and an acceptance test
  diffing the viewer's output against the real game's capture.
- **Importmap drift** — this repo's most-tripped footgun now spans FOUR html
  files; a consistency-checker script guards it.
- **Deliberately NOT doing:** fixing any layout violation the linter finds
  (that's the grammar change's job — this change only records the baseline),
  and the builder dry-run split (deferred, see Key Decisions).
