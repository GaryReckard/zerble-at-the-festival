## Pragmatist's Position

**TL/DR:** Proceed with the architecture, but implement two complete vertical slices before migrating every population. Children prove an independently owned population, and Healing Arts proves borrowed identity and rendering authority. Those two production consumers should shape the common contract before it spreads through the game.

### Critical Path

The essential dependency chain is **characterize current ordering and ownership → establish a production-backed mixed fixture → complete one independent population → complete one borrowed-person activity → migrate the remaining families → consolidate scheduling and remove transitional paths**. This is a proposed delivery order, not a claim that these modules already exist.

The current plan groups all focused population extractions ahead of the renderer/activity work and leaves the extension proof until the final acceptance group (`openspec/changes/people-npc-architecture/tasks.md:28-47`, `:65-70`). That order risks teaching several controllers an interface which has only been tested against the easiest ownership model. The source already gives us a useful contrasting consumer: children own their meshes and per-child state (`src/obstacles.js:389-454`), whereas Healing Arts borrows crowd identity and calls a private rendering method when releasing it (`src/healingArtsActivity.js:21-50`). Validate both before broad rollout.

Ordering characterization is mandatory. Vehicles run before registry synchronization and Crowd, while roaming groups and place activities run later (`src/main.js:1193-1196`, `:1219-1244`); Crowd itself ticks camp sessions and parties before individual updates (`src/crowd.js:910-950`). Collecting these into one early update would be a behavior change. The proposed legacy slots are the right migration device, provided each replacement removes its old invocation and a trace proves exactly one execution owner.

### Priority Sequence

1. **Inventory everything, but build executable evidence in the order of migration.** Complete the owner/update/collision inventory for all families first. Establish a comparable Low/Mid baseline and direct collision-order checks, then add detailed behavior cases immediately before each affected slice. Do not require exhaustive implementation of every final activity scenario before the first controller can migrate. The current foundation checklist requests broad coverage (`openspec/changes/people-npc-architecture/tasks.md:15-18`); the existing photographer, Healing Arts, camp and monk verification surfaces allow incremental reuse instead (`DEBUGGING.md:559`, `:591-605`, `:623-635`). This changes sequencing, not final coverage.

2. **Build the narrow workshop and contract spine together.** Add the mixed production fixture, registration validation, execution counts, inspection, lifetime-safe handles, and reusable collision sinks, then migrate children fully through them. Keep adult Crowd wrapped at its existing update location. Prove that a fixture population can join without changing character-specific main update, honk, collision, debug, or cleanup branches at this stage, rather than waiting for final Task 7.4 (extension proof) (`openspec/changes/people-npc-architecture/tasks.md:70`). The one-URL surface is a project requirement (`AGENTS.md:43-55`), not a new testing framework.

3. **Prove activity and rendering authority with Healing Arts next.** Implement only the public crowd access/binding operations and claim semantics this real consumer requires. Cover its current spawning/adoption and release flows, preserve one crowd person, and remove its direct private rendering call (`src/healingArtsActivity.js:28-50`). Test tent unload through the real owner path, which disposes the activity before registry removal (`src/chunks.js:587-595`). This is the architectural force multiplier: it tests identity, movement authority, alternate rendering, spatial visibility and unload without waiting for every activity to migrate.

4. **Migrate remaining independent families and the remaining shared-person consumers.** Once both ownership models work, finish wooks, formations, hoopers and frisbee pairs, then monks and the remaining activities. Keep the full inventory as the completion ledger. Monks are a mandatory group/vehicle acceptance case because they currently spawn crowd records, replace avatars and write private matrices (`src/monks.js:30-49`); camp music is a mandatory resource/audio case because it already validates job owners and attaches bounded session audio (`src/campJamActivity.js:21-41`). Reuse their policies instead of designing replacement behavior.

5. **Complete consumer adapters before changing dependency order.** Migrate neighborhood queries and vehicle/seat dependencies with their original filters. One-wheel yielding currently reads the crowd array and excludes particular activity states (`src/oneWheels.js:73-86`); publishing all people must not silently broaden that behavior. Preserve registry-first collision order, persistent moving-group collider references, crowd exclusions and scratch reuse (`src/main.js:1514-1538`). Only after equivalent traces and scenarios pass should transitional slots become named dependency phases.

6. **Retire obsolete paths and finish acceptance across the whole inventory.** Remove the obstacle collection and private cross-controller writes after their consumers migrate. Run every promised contract, mixed workshop, Low/Mid game boot, collision and unload/revisit check, and comparable performance measurement. The final extension proof confirms a practice already established in the first slices. Final acceptance must inspect every ledger row, not merely confirm that the coordinator exists (`openspec/changes/people-npc-architecture/design.md:194-216`).

### Incremental Delivery Plan

- **Slice 1 (ship first): Evidence and the independent-population path.** Deliver the baseline inventory, production mixed fixture, thin runtime and a complete child migration. Adult instancing stays in its existing implementation, and unrelated controllers continue their current paths until their own slice. Verify adult/child reactions and smiles, child relocation identity, stale handles, one execution per slot, collision candidate equivalence, repeated teardown and real-game boot. Child relocation currently moves the same mesh and resets its scatter timer (`src/obstacles.js:495-514`), so define whether this preserves identity before assigning generations. The slice is useful immediately because a future independent family has an integration recipe.

- **Slice 2 (ship after): Borrowed identity and bindings.** Add the minimum crowd render facade, public person commands and generation-safe activity claims needed by Healing Arts, replacing its existing private access. Verify arrival, class exit, dance, interruption, owner unload, restoration of the ordinary binding and stale release after reassignment through the existing `healing_arts_activity` fixture (`DEBUGGING.md:597-606`). This depends on Slice 1's handles and fixture, and provides the second integration recipe.

- **Slice 3 (ship after): Complete the remaining people and activity migrations.** Deliver separate reviewable increments per family/activity, each including its query/interaction/collision facets, ownership cleanup and production fixture. Preserve monk all-or-none boarding, vehicle despawn release, and camp resource identity checks (`src/monks.js:30-49`, `src/nutWagon.js:216-225`, `src/campJamActivity.js:25-29`). This is still required refactor work, not a deferred follow-up.

- **Slice 4 (ship after): Complete adapters, consolidate scheduling and remove transition code.** Finish place/vehicle participation and consumer query migrations, then consolidate proven dependencies and run acceptance across all families. Preserve chunk-owned performer removal (`src/chunks.js:596-597`), independently registered one-wheel collision bodies (`src/oneWheels.js:70-71`) and Crowd's instanced dirty uploads (`src/crowd.js:953-968`). Require full-game streaming verification because the sandbox cannot establish those ownership paths (`AGENTS.md:59-64`).

For every slice, update its extension documentation and verification evidence as part of delivery. A new workshop or debug workflow needs a same-commit changelog entry; final Task 7.5 (documentation and audit trail) must be a reconciliation pass rather than the first documentation update (`openspec/changes/people-npc-architecture/tasks.md:71`, `.claude/rules/changelog-and-roadmap.md:8-25`). All new source modules belong in five importmaps and must pass `bin/check-importmaps` (`.claude/rules/no-build.md:19-41`).

### Deferred / Park on ROADMAP

- **Crowd scheduling optimization and simulation LOD:** Keep the existing measurement gate. Neither is required to establish registration, identity, activity or rendering boundaries; neighborhood-query scheduling changes already have a dedicated roadmap entry (`ROADMAP.md:53-56`). This refactor should make later optimization easier without claiming it as a prerequisite.
- **Crowd pre-roll and pure world-builder extraction:** Keep the existing worldgen follow-up intact. Its stated purpose is tier-independent record generation and exact headless layout extents, while this refactor preserves the current production draw streams (`ROADMAP.md:106-122`). Do not accidentally absorb a change to population RNG consumption into module cleanup.
- **Full replay, ECS storage, behavior-tree replacement, a population director and a generic resource transaction engine:** Preserve these as evaluated alternatives rather than creating additional required phases. The critical evaluation supplies the disposition of each (`openspec/changes/people-npc-architecture/critical-evaluation.md:17-34`), and the proposed integration boundary does not depend on implementing them. Reconsider only against a concrete future requirement. Existing camp jobs already have local ownership validation and teardown semantics to reuse (`src/campJamActivity.js:10-29`).
- **New models and replacement render storage:** No downstream refactor work requires them. Keep the existing shared NPC geometry/material resources (`src/models/puppet.js:79-95`), child articulated rigs (`src/obstacles.js:413-445`) and adult instance batches (`src/crowd.js:953-968`). This avoids coupling an ownership migration to visual or rendering redesign.

The remaining listed families, activity cleanup, public boundaries, shared rules with proven consumers and final extension checks are required completion work. They are not candidates for indefinite deferral. Freeze behavior is not a milestone for this plan; a coherent integration and ownership contract is the deliverable described by the proposal (`openspec/changes/people-npc-architecture/proposal.md:1-17`).

### Verdict

- **Verdict**: Proceed with mitigations.
- **Key Concern**: Horizontal framework and family migrations can multiply an unproven ownership contract before borrowed identity and render handoff have tested it.
- **Recommendation**: Adopt the thin runtime, stable identities, explicit authority and ordered providers, but promote the extension proof and a Healing Arts vertical slice ahead of broad controller rollout. Preserve current call order and RNG streams, include documentation and evidence in each slice, and require the complete migration ledger before declaring the refactor finished. This is a planning recommendation; no runtime code, browser measurement or implementation test result is claimed here.
