### Vulnerabilities Found

- **Support observation can accidentally become support transition. Severity: High.** `groundOnSurface()` samples the center, four wheel locations and repeated suspension corrections (`src/zerble.js:1231`, `src/zerble.js:1236`, `src/zerble.js:1252`). Driving also samples a proposed location before deciding whether to accept it (`src/terrainDriving.js:43`). If a stateful sampler commits a support change on any of these reads, wheel iteration or a rejected proposal can move the whole cart between terrain and deck. The design correctly prohibits silent layer changes but does not yet define the commit boundary (`design.md:21`). **Blocking correction before Group 2 (pure support/solid contracts) implementation:** Task 1.2 (support semantics) must distinguish read-only sampling on a selected layer from a proposed transition that commits only with an accepted mover pose. Specify approach boundary behavior for a footprint straddling the terrain/deck join, and define a blocked result that cannot silently become terrain fallback. Add a rejected-proposal test and permute wheel sample order. This implements the existing contract rather than broadening it.

- **The cart adapter is needed before its current ownership assignment. Severity: High.** Group 3 (engineering proof) owns fixture, sandbox and HTML files, while explicit runtime adapters and `terrainDriving.js` are assigned to Group 4 (authoritative travel), despite the earlier group requiring real-cart bridge traversal (`tasks.md:24`, `tasks.md:28`, `tasks.md:35`). The existing sampler is stateless and the controller rejects only the candidate center's `traversable` flag (`src/terrainDriving.js:44`). **Blocking correction before Task 3.2 (authored landscape sandbox):** assign the minimal support-state binding to Group 3 (engineering proof), including its opt-in cart hooks, while retaining full-footprint blocking and global contact publication in Group 4 (authoritative travel). Document which behavior the earlier bank test proves; do not let a center-only refusal count as recoverable whole-footprint barrier acceptance (`tasks.md:38`). Preserve the current grounding algorithm and suspension bounds, whose history is attributed to Gary in commit `7b992a1`; these are not incidental cleanup targets (`src/zerble.js:1240`, `src/zerble.js:1255`).

- **Existing ray and timing checks can falsely certify the layered proof. Severity: High.** The current verifier fires from Y=100 and accepts the first mesh hit, which selects an overhead deck for an underneath pose if both surfaces enter that mesh list (`src/terrainSandbox.js:209`). Its save/restore currently preserves only position, heading and speed, so new support state must also be restored (`src/terrainSandbox.js:197`, `src/terrainSandbox.js:227`). Separately, the loop always calls `cart.update(1 / 120, ...)`, regardless of display cadence (`src/terrainSandbox.js:249`). **Blocking correction before Task 3.3 (ray/contact and rate proof):** identify the expected surface's actual mesh when checking rays, test terrain and deck independently at overlapping X/Z, save/restore support state, and call the real controller with 1/30, 1/60 and 1/120 inputs in the rate regression. A browser display-rate change alone is insufficient. Retain finite complete input objects because `Zerble.update()` reads input immediately (`src/zerble.js:1267`).

- **Atomic publication is not provided by the registry. Severity: High.** Task 5.1 (complete district ownership) asks for atomic publication, but entries become visible in live broadphase structures during `Registry.add()` (`tasks.md:48`, `src/registry.js:64`). Pure admission before building does not undo registry entries, sound or graphics if a later builder throws. **Later acceptance gate before Group 5 (populated district) closes:** stage side effects or keep an explicit owner release ledger, inject failure after partial construction, and verify no scene/registry/audio residue after retry. Also demonstrate pin release and opposite-direction revisit rather than relying solely on stable plan IDs (`tasks.md:51`). This does not block the pure fixture.

- **Dropped-prop acceptance precedes the adapter that makes it meaningful. Severity: Medium.** Task 7.4 (functional stream crossing) requires representative dropped props, but Task 8.4 (physical-prop surface adapter) supplies their shared terrain/version/owner integration, and Group 8 (consumer migration) depends on Group 7 (water systems) (`tasks.md:73`, `tasks.md:79`, `tasks.md:84`). The current physical runtime explicitly describes its slope as a fixture plane and production terrain/registry integration as pending (`src/physics/runtime.js:101`). **Concrete planning correction before reaching Group 7 (water systems):** make the dropped-prop portion of crossing acceptance depend on Task 8.4 (physical-prop surface adapter), or move that narrow adapter ahead of final crossing acceptance. A separate plane fixture cannot close this gate.
