### Experience Concerns

- **Player: safe reading is the highest priority.** Neutralizing new controls does not itself freeze the world. The current loop updates the cart with neutral input only when existing locks apply, updates bubbles independently, and advances Festival Run timers (`src/main.js:973,1076,1099,1109`). A player should be able to read earned memories without running dry or returning to a collision. Pausing only collection would also allow real-world events to happen without entering the passport, undermining the promised honest measurement (`design.md:6`, change `specs/festival-passport/spec.md:8`).
- **Player: make statistics understandable beside the HUD.** Use “Smiles collected” with a brief “before score bonuses” explanation, rather than presenting raw smiles as the current score. The score system deliberately distinguishes collected smiles from multiplied points (`src/scoring.js:55-62,80-85`). Label distance from the entrance separately from distance driven, present current distance in the visit context rather than as an all-time additive total, and retain the proposed note that older distances and stage counts begin with this feature (`design.md:6,9,14`).
- **Player: keep the passport celebratory without turning mistakes into objectives.** The plan counts damaging bonks as well as exploration (`proposal.md:7`), while the player guidance explicitly discourages hitting people (`README.md:90`). Show bonks as an honest statistic, but reserve celebratory stamps for exploration and positive interactions. Keep achievement criteria separate from bubble powers, since the existing upgrade view already offers earned toggles and charm explanations (`src/upgradesMenu.js:22-24,46-56`).
- **Player: protect discovery.** The spec promises readable earned and unearned stamps without defining secret treatment (`specs/festival-passport/spec.md:19`). Restrict the initial catalog to the proposed public counters, and do not enumerate hidden activities incidentally through stamp names, totals or criteria. Existing Mushroom Bubbles deliberately hide their pre-earned identity (`src/bubbleTypes.js:61`); README and title copy must continue honoring the explicit discovery rule (`AGENTS.md:135-137`).
- **Next agent / dev: modal correctness needs behavioral drills.** The upgrade menu provides a useful focus trap and restoration pattern (`src/upgradesMenu.js:114-142`), but keyboard state is retained until keyup or blur, and focusing an ordinary dialog button does not trigger the editable-field clearing rule (`src/input.js:31-51`). Verify that holding drive or boost while opening the passport, releasing it inside the overlay, and closing cannot resume stale motion. Check touch stick release and camera gestures as well, including scroll gestures within the panel (`src/input.js:86-100`, `src/touch.js:47`).
- **Next agent / dev: preserve a single truth for earned progress.** The proposal correctly keeps bubble unlock ownership in its current store (`proposal.md:15`), whose lifetime smile total is mutable and persisted independently (`src/bubbleProgress.js:94-109,123-127`). Test the migrated passport total beside the existing “1,000 smiles, all-time” upgrade criterion, especially around storage failure and reload, so the player does not see unexplained disagreements (`src/bubbleTypes.js:55`, `design.md:14`).
- **Cognitive Load:** This visit / All time is a useful two-level model, but a third achievement system must explain its relationship to existing score and upgrades. Keep the passport a read-only record, preserve upgrades as the control for bubble effects, and put browser-local persistence and historical-coverage wording near the relevant totals. These boundaries follow the proposal's separation of progress ownership and the explicit storage wording requirement (`proposal.md:15`, change `specs/festival-passport/spec.md:16`).

### Experiences Not Addressed

- As a player, I would expect opening a modal record to give me time to read, but the current acceptance contract covers input suppression and counter gating without specifying resource, collision or run-clock behavior (`design.md:6`, change `specs/festival-passport/spec.md:19`). Add a pause/resume scenario that proves these outcomes.
- As a player, I would expect stamp criteria to tell me what to try next, but no stamp catalog or scope is defined in the proposed requirements (`specs/festival-passport/spec.md:16`). Add it before writing tests or player documentation.
- As the next agent, I would be unable to inspect populated passport layouts and save-failure states in seconds using the proposed task list alone. It defines no fixture URL or passport debug drill (`tasks.md:2,7,9`). Add the DOM preview and local inspection API before feature hooks; an entity geometry preview is unnecessary for this DOM surface, while the actual game remains necessary for lifecycle verification (`AGENTS.md:45-56,63-69`).

### Verdict

- **Verdict**: Proceed with mitigations
- **Key Concern**: The player must be able to read the passport safely, and counter suppression alone does not establish that behavior.
- **Recommendation**: Specify and test pause/resume, stamp criteria and a reusable populated DOM preview before integrating gameplay hooks. The pure-store/DOM separation, browser-local persistence and incremental analytics are a sound basis for a warm, understandable record of exploration (`design.md:4-6`).
