## The Profiler's Position

TL/DR: Run the first structural proof against exact pedestrian support reuse, with a bounded static-rendering proof as the competing hypothesis. The current evidence supports investigating both, but does not establish an FPS benefit for either. Explicit registry publication is a credible smaller fallback; a whole-engine rewrite is not justified by these captures.

### Priority Sequence

1. **Separate the objectives.** Use stationary scenes to assess steady rendering/simulation cost and the driving route to assess tails and construction. The last terrain change reduced measured CPU work but did not clear the primary delivered-frame threshold, while worst driving frames remained 130.50 ms. It demonstrates why a fast subsystem benchmark cannot select the next architecture alone (`verification/performance/2026-11-06-terrain-sampling/lattice-README.md`, “Runtime comparison”).
2. **Prove exact pedestrian support reuse first.** High/Low inclusive support-binding `propose` attribution is 7,858/5,037 sampled ms, and terrain sampling is 6,647/4,212 ms; these overlap and must never be added. This is a substantial CPU target on both tiers, without requiring more geometry, different physics cadence or visual reduction (`verification/performance/2026-11-07-structural-options/{high,low}-route-all-functions.json`, `inclusive`, functions at `src/landscape/support.js:147` and `src/worldgen/terrain.js:219`).
3. **Give bounded static presentation one fair competing experiment.** High/Low self attribution includes 3,316/2,252 ms in world-matrix traversal and 3,109/1,708 ms in projection. These totals span the scene, so first identify which families actually own that cost rather than assigning all of it to static props (same attribution files, `self.updateMatrixWorld` and `self.projectObject`).
4. **Retain an explicit-publication registry option, then investigate specialized tails.** Registry reconciliation has 2,375/2,358 ms inclusive attribution on High/Low and still scans every entry, whereas ordinary generation accounts for only 165/134 ms cumulatively. The latter remains a possible tail cause, but it is not the best supported general-throughput rewrite (`src/registry.js:308-333`; attribution files, `inclusive.rebuildSpatialIndex` and `inclusive._generate`).

### Budget Estimate

- **Draw delta**: The proposed support and registry paths target **0 additional draws** by retaining presentation. A static batch has a conditional per-pass delta of `B - N`, where `N` is the eligible ordinary submissions actually replaced in that camera/pass and `B` is the nonempty replacement batches. Neither number is established by unculled topology. Low's 80-draw guide is the tightest nominal budget, followed by Mid's 200 and High's 400 (`src/debug.js:35-46`). Absolute post-change headroom cannot be calculated from the supplied topology.
- **Triangle delta**: Support/registry target **0 additional triangles**. Static representation retains source geometry, but a coarser visible batch may submit additional offscreen member triangles, so its submitted-triangle delta is unknown rather than assumed zero. Compare actual scene and shadow-pass submissions against Low 150k, Mid 400k and High 1.2M (`src/debug.js:35-46`; `src/people/childPresentation.js:87-105`).
- **Cost type**: Support and registry primarily target **steady-state CPU work**. Static presentation targets steady CPU submission/traversal with a potential GPU tradeoff and construction/upload cost. Bounded construction specifically targets **allocation/construction tails**, because its present deadline only controls admission (`src/landscape/support.js:147-165`; `src/registry.js:308-333`; `src/chunks.js:384-397`).
- **Low/mid-tier verdict**: **Safe in rendering budget for support/registry, conditional on exact semantics and bounded cache retention; static rendering remains at risk until measured.** Low already uses a 1.25 pixel-ratio cap and shadows off, while Mid uses 1.5 with shadows on. Do not import the historical 1.0 Low cap or a fixed one-chunk-per-frame claim into the plan (`src/perf.js:100-105`, `src/perf.js:173-178`; `src/chunks.js:384-389`). No proposed path needs a new light, caster, texture or post-process pass; preserve idle-pass gating and shared-disposal rules (`.claude/rules/performance.md:83-116`).

### Ranked Candidates

1. **Exact support-region reuse or coherent batched queries.** This is my preferred first proof, not an approved production rewrite. The service already has stable terrain-cell planes, but every binding proposal walks sweep points and complete contact footprints, while the sampler repeats water classification (`src/worldgen/terrain.js:195-225`; `src/landscape/support.js:138-165`). Investigate generation-keyed reusable query context that amortizes immutable owner/cell/water/deck lookup while preserving each required sample's arithmetic and ordered transitions. A region fast path must prove the entire swept footprint remains in a region with unchanged support and exclusion semantics, otherwise fall back to the existing path. A plane is insufficient evidence on its own. Do not propose removing duplicate immediate commit validation because that optimization is already present (`src/landscape/support.js:185-190`; `src/landscape/peopleAdapter.js:30-35`).

2. **Spatial static presentation with a separate render ownership layer.** Potentially the largest rendering restructuring, but keep gameplay entities and their chunk/lake ownership intact. The Low snapshot has 7,751 nodes, 5,770 mesh objects and 3,790 visible plain opaque meshes; its 1,578 repeated-object upper bound includes unknown/dynamic eligibility and camera layers, so it is an opportunity inventory, not 1,578 saved draws (`verification/performance/2026-11-07-structural-options/low-scene-topology-summary.json`). Start with immutable repeated families that already share actual geometry/material identity, using bounded spatial batches whose independent disposal borrows pooled resources. Reject a generic merge pass in light of the previous real-GPU failure (`docs/backlog/performance.md:107`). Static islands that merely freeze matrices may reduce matrix work but retain projection and submissions, so distinguish that mechanism from instancing in the experiment.

3. **Explicit registry spatial publication.** This has unusually clear cross-tier attribution and removes discovery rather than introducing another spatial index. Existing cells are already retained; the actual target is scanning raw state, rebuilding oversized-entry order and maximum query padding every frame (`src/registry.js:305-333`). Keep a small known-moving set and explicit shape-change publication, with aggregate maintenance that handles shrinking/removing the previous maximum. Preserve the current synchronization boundary and callback candidate order (`src/main.js:1463-1474`; `src/registry.js:341-345`). It is a defensible fallback if support reuse cannot achieve useful exact coverage, but not evidence that the whole registry needs replacement.

4. **Deterministic child contact solving.** Measure actual passes, candidate tests and corrections before extraction. The 128-pass ceiling is an upper bound with early exits, and the existing pair-order and world correction semantics make a naive precomputed grid unsafe (`src/people/children.js:411-455`). Whole child-update attribution is only an upper bound on solver savings: 2,170/1,686 sampled ms High/Low (`high-route-all-functions.json` and `low-route-all-functions.json`, `inclusive.update`, `src/people/children.js:180`).

5. **Cancellable bounded ordinary-world construction.** Promote this above the throughput candidates only if timeline evidence places ordinary construction inside the measured worst frames. Its correct goal is better tails, not parked FPS. Reuse the existing district iterator/deadline/cancel shape rather than inventing an unrelated scheduler, and preserve completed-owner publication (`src/landscape/districtBuild.js:6-31`; `src/chunks.js:332-343`). A 165/134 ms cumulative sample total does not rule out a rare expensive builder, but it cannot establish one either (High/Low attribution, `inclusive._generate`).

6. **Compact child poses.** This can remove retained source-rig traversal, but draw submission is already instanced and the presentation sync itself accounts for only 232/216 ms inclusive High/Low. Ancestor traversal savings are not isolated by those totals, so attribute source rigs before replacing the hierarchy (`src/people/childPresentation.js:23-25`, `src/people/childPresentation.js:43-54`, `src/people/childPresentation.js:69-105`; attribution files, `inclusive.sync`).

7. **Incremental ground representation.** Defer this structural choice unless a new frame-local trace overturns the small current target: complete resampling accounts for 138/145 sampled ms High/Low, and the exact-lattice shortcut already exists (`src/world.js:211-228`; `src/worldgen/terrain.js:227-239`; attribution files, `inclusive.resampleGroundSurface`). The previous complete-ground CPU reduction did not produce a detectable primary frame-delivery improvement, which is strong evidence against immediately adding tile seams, normals ownership and extra draw boundaries (`verification/performance/2026-11-06-terrain-sampling/lattice-README.md`).

### Discriminating Experiments

Only the orchestrator should execute these experiments. Freeze the current dirty terrain baseline in a source manifest, and change one mechanism at a time. Preserve the lab's source/build identity, fixed content, independent-run comparisons, fresh calibration/holdout and segment regression protection; diagnostic CPU profiles remain separate from accepted timing comparisons (`docs/performance-lab.md`, “Offline commands” and “Browser commands”; `verification/performance/2026-11-07-structural-options/candidate-inventory.md`, “Observed baseline”).

1. **Support feasibility and coverage, before a runtime rewrite.** Capture a bounded sequence of actual pedestrian support requests with generation identity, selected support, sweep/contact inputs and all returned fields, then replay it against the unchanged service and one reusable-context prototype. Include triangle diagonals, cell edges, negative coordinates, grade thresholds, water boundaries, overlapping deck approaches, missing/departed owners and terrain-generation changes. Retain exact existing sample arithmetic and operation order; reject a path if any accepted position, support identity, traversability, block reason, height or slope changes. Report region hits, fallback reasons, queries avoided, bounded retained bytes, cold construction cost and warm replay time. Keep request-capture overhead out of final timing runs. These cases follow directly from the existing sampler, support state machine and full footprint sweep (`src/worldgen/terrain.js:192-225`; `src/landscape/support.js:82-119`, `src/landscape/support.js:138-165`). **Overturn my preference** if safe coverage is poor, predicate/classification cost consumes the saved work, or retaining exact semantics requires a larger rewrite than the measured target warrants. A high cache-hit percentage alone is insufficient.

2. **One-family static presentation proof, against the same current baseline.** First attribute the chosen immutable repeated family and count its eligible source objects, camera-visible submissions and casters. Compare ordinary objects with spatial instance batches while retaining identical transforms, geometry, materials, layer eligibility and gameplay ownership. Test the actual Noon/Midnight views, all three camera modes, manual camera movement, spatial boundaries, unload/reload and Mid shadows. Record scene draws/tris separately from shadow work, matrix/projection time, buffer upload, build cost and retained resource counts. Do not infer eligibility from the topology upper bound or attach the complete scene's matrix cost to the selected family (`low-scene-topology-summary.json`; `src/people/childPresentation.js:35-47`, `src/people/childPresentation.js:69-114`). **Promote this candidate above support** if it provides a larger reproducible delivered-frame improvement with no protected segment/GPU/content regression; **reject it** if submission or triangle inflation repeats the prior merge failure (`docs/backlog/performance.md:107`).

3. **Timing gate, plus tail attribution on the existing route.** Advance only the mechanism that survives its feasibility proof into an unprofiled paired real-game comparison. Use Low and High to discriminate tier behavior, then Mid to verify shadow-bearing behavior; retain equal content and fixed quality, and report frame delivery, p95/p99, stalls and protected route segments. Collect frame-local builder/ground-recenter durations in a separate diagnostic pass before attributing remaining spikes to ordinary streaming. For a target whose work improves but whose delivered frames do not, record CPU headroom as that narrower result and choose explicitly whether it merits maintenance cost. The terrain report supplies the exact precedent: a 2 ms primary bound was not cleared even though a secondary driving p99 improvement was detected (`verification/performance/2026-11-06-terrain-sampling/lattice-README.md`, “Runtime comparison”). Use fresh calibrated bounds for the new baseline rather than assuming that old 2 ms bound applies unchanged (`docs/performance-lab.md`, “Offline commands”).

No player-visible quality reduction is proposed. If a prototype requires different culling, delayed visible publication, reduced terrain, changed population or skipped offscreen simulation, it has changed the question and needs a separately named content/tradeoff experiment, rather than being credited as the same-work optimization (briefing, “Constraints”; `docs/performance-lab.md`, equal-work comparison policy).

### Scope and Evidence Limits

The historical `.Codex` performance paths are absent in this checkout; the current equivalents read for this position are `.claude/rules/performance.md`, `.claude/perf-audit-plan.md` and `.claude/perf-pass-2-plan.md`. This is a Markdown-only independent assessment, with no production code edits, browser launches, servers, tests or benchmark execution. The supplied measurements establish fixed desktop observations, not physical-phone performance or GPU duration. Low and Mid profiles on the Mac are necessary policy checks, while physical-device acceptance remains separate (`docs/performance-lab.md`, “Current acceptance”).

### Verdict

- **Verdict**: Proceed with mitigations
- **Key Concern**: Structural CPU reductions can fail to improve delivered frames or can regress GPU work; support reuse must additionally prove complete water/deck/footprint truth.
- **Recommendation**: Select exact support reuse for the first bounded proof, with static presentation as its competing mechanism, and defer exhaustive production planning until a controlled real-game comparison discriminates them.
