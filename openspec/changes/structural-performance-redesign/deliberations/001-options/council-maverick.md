## Maverick's Position

TL/DR: Investigate explicit registry publication first because it removes repeated discovery without buying performance through a thinner festival. Keep exact support regions as the higher-upside second candidate, and use a matrix-only render probe to distinguish whether spatial batching earns its complexity. No production rewrite is justified yet.

### Priority Sequence

2. **Measure the publication contract before committing to its redesign.** Inventory entries whose position, footprint, collider membership or radius changes at the existing spatial barrier, then compare an experimental explicit-publication result against the current scan's ordered queries and exact aggregates. Keep immediate generation-time add/remove visibility, the existing frame barrier, and physical-entry synchronization where they currently occur (`src/registry.js:89`, `src/registry.js:125`, `src/registry.js:216`, `src/main.js:1463`).
3. **Keep the higher-upside support opportunity alive with an eligibility measurement.** Binding-level support proposals receive approximately 7,858 ms inclusive attribution on High and 5,037 ms on Low, but those overlap terrain and adult costs and cannot be added to them. The existing move API already removes duplicate commit validation, so a new design must prove it avoids actual repeated geometry evaluation while retaining every swept center and footprint test (`high-route-all-functions.json`, `low-route-all-functions.json` in the evidence directory; `src/landscape/support.js:138`, `src/landscape/support.js:147`, `src/landscape/support.js:185`, `src/landscape/peopleAdapter.js:30`).

### Selection and Scope

**Select the registry-publication investigation, with production selection conditional on its result.** Make the structural change about ownership of spatial truth rather than introducing a new entity framework. The current store already owns live insertion/removal, ordered spatial state and a physical synchronization path, so another registry or an ECS migration would duplicate those capabilities (`src/registry.js:89`, `:125`, `:216`, `:308`). Its compounding value is an explicit contract that future movers can satisfy without making all static content pay a discovery cost; this is a proposed benefit, not a measured result.

The first experiment must not silently classify everything by `kind` or `chunkKey`, because the registry contract allows entries without chunk ownership and its live values are mutable. Add/remove, removal before frame synchronization, footprint threshold transitions, radius changes and physical owner transfer all need to preserve their existing behavior (`src/registry.js:125`, `:216`, `:242`, `:308`, `ARCHITECTURE.md:362`). Keep lakes independent of chunk unload and leave full-game simulation running offscreen (`AGENTS.md:98`, `ARCHITECTURE.md:975`). No player-visible tradeoff is accepted: density, terrain detail, accepted clocks and camera freedom stay part of the protected comparison, rather than becoming tuning knobs (`AGENTS.md:131`, `ARCHITECTURE.md:984`, briefing constraints).

Respect the currently approved Vite workflow and pinned Three/shim path; the older no-build/importmap instructions in configuration and council text are superseded (`AGENTS.md:86`, `.claude/rules/no-build.md:17`, `:23`). Preserve synchronous gesture audio, RNG ordering and disposal/dirty flags throughout any later experiment (`AGENTS.md:92`, `:95`, `:102`, `:105`). This deliberation writes only this Markdown and proposes no new dependency.

### Smallest Discriminating Experiments

Only the orchestrator should run captures. These are sequential choices, not a request to build seven prototypes.

1. **Registry shadow publication followed by one bounded runtime probe.** On the existing frozen route, record which entries actually change spatial fields and which owner performs the write, including raw mutation paths. An instrumented shadow implementation should produce exactly the existing ordered query candidates, oversized-entry order and query pads at every existing publication boundary, including immediate add/remove and the physical sync path. Exercise radius shrink/growth, threshold crossings, moving-entry removal, unload/revisit and owner transfer separately. The need follows directly from the scan's current responsibilities and physical-path updates (`src/registry.js:216`, `:242`, `:308`). If an explicit changing set cannot be complete without repeatedly scanning the static population, stop this candidate. If it can, create a bounded experiment that actually replaces the scan, and measure it separately with ordinary timing rather than using the shadow run as performance evidence.
2. **One exact-support eligibility probe if registry evidence is weak or the measured gain is too small.** Count full proposal/footprint calls that could reuse an immutable exact region, fallback reasons, region construction cost and retention. Compare complete support outputs and accepted poses against the current proposal sweep, with water/deck approaches, grade boundaries, turns, missing support and world replacement represented. Do not batch acceptance across movers or reorder their updates; the current binding performs ordered intermediate steps and owns accepted state (`src/landscape/support.js:98`, `:154`, `:174`, `:198`). A low route-weighted hit rate, expensive validation or any support mismatch should end the experiment before a broad terrain rewrite.
3. **One controlled comparison for the winner.** Freeze the source and semantics, verify the affected real-game paths and tier startup, then use the established calibrated ordinary-timing comparison for parked and driving High/Low. Select delivered-frame metrics and a meaningful detection threshold before running. Report work headroom separately, and retain the primary no-change outcome if that is what the measurements show. Match all camera modes/manual movement, shadows, content and owner lifetimes; record construction cost and steady-state cost separately (`AGENTS.md:56`, `:63`, `:109`, `ARCHITECTURE.md:1024`, `verification/performance/2026-11-06-terrain-sampling/lattice-README.md:64`). A passing desktop probe can justify implementation planning but cannot close Auto or physical-iPad acceptance (`ROADMAP.md:257`, `:262`).

**Evidence that would overturn this ranking:** A per-frame trace tying the remaining worst stalls to an ordinary builder would promote cancellable construction; a complete support-region probe showing high reuse and materially lower work would promote support ahead of registry; a verified eligible static family with real-GPU delivered-frame gains would promote spatial presentation. Conversely, absent detectable delivery gains and absent a separately agreed headroom objective, recommend no production restructuring. The current evidence does not already establish any of these outcomes (`candidate-inventory.md:9`, `:26`, `:30` in the shared evidence directory; `verification/performance/2026-11-06-terrain-sampling/lattice-README.md:64`).

### Alternative Approach

**Test static transform publication without first changing mesh submission.** Before spatially batching models, use a narrowly audited owner with immutable transforms and compare ordinary matrix updates against one-time matrix publication with explicit invalidation. Keep the same meshes, materials, layers, bounds, camera eligibility and shadows, so this test isolates redundant transform evaluation from draw submission and frustum granularity. This is a proposed experiment, not a claim that a blanket matrix flag is safe or that traversal disappears. Current profiles distinguish `updateMatrixWorld` from `projectObject`, making that distinction worth testing (`high-route-all-functions.json`, `low-route-all-functions.json` in the shared evidence directory).

Do not freeze all descendants of a chunk or lake group. Children deliberately retain animated source hierarchies, loaded lakes drift their canoes, district detail has its own camera-distance publication, and camp props can acquire live physical transforms. Those are concrete counterexamples to assuming owner residency means immutable presentation (`src/people/childPresentation.js:23`, `src/lakes.js:137`, `src/landscape/districtVisibility.js:19`, `ROADMAP.md:225`). A source audit and exact world-matrix comparison must identify eligibility, including parent changes, before the probe; if a useful static island cannot be established cheaply, abandon it.

- **Value**: The experiment separates two rendering hypotheses while preserving the full festival and existing gameplay ownership. If matrix evaluation alone is material, it could avoid the additional lifetime, bounds and culling machinery of spatial batches; if projection dominates the eligible family, that negative result strengthens the batching case. The distinction comes from the separate renderer attribution, not an assumed gain (`high-route-all-functions.json`, `low-route-all-functions.json`).
- **Risk**: Hidden transform writers or parent changes can leave stale geometry and shadows, so this must be an explicitly eligible island with invalidation and exact transform/camera checks. It does not address GPU submission by itself, and the previous broad merge failure remains a warning against extrapolating a CPU-only success (`src/people/childPresentation.js:51`, `docs/backlog/performance.md:110`).
- **Effort**: Lower than converting multiple model families into a new spatial batch owner, provided the eligibility audit finds an actual immutable family. Reuse the existing owner and pooled resource lifecycle, and avoid reviving the separately deferred pure-builder extraction or adding another worker system (`AGENTS.md:102`, `ROADMAP.md:139`, `ARCHITECTURE.md:1000`).

### Verdict

- **Verdict**: Proceed with mitigations
- **Key Concern**: A large attribution number or a cleaner architecture can still produce no player-visible improvement, as the terrain comparison already demonstrates (`verification/performance/2026-11-06-terrain-sampling/lattice-README.md:64`).
- **Recommendation**: Proceed with the registry-publication experiment, retain exact support regions as the next high-upside discriminator, and defer production selection until an ordinary-timing comparison earns it. Preserve festival richness and all ownership/camera/support contracts; choose no rewrite if the evidence does not justify the migration.
