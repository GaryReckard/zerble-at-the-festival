## Tension T3 — REVISED slice plan (smallest diff that moves the PRODUCTION number)

My R1 plan is **superseded** on two points: (a) Slice-0's free win doesn't exist in production, and (b) Slice 1 targeted the wrong (v1) scatter path. Here is the corrected, critical-path-disciplined plan.

### Does Slice 1 now target v2 `scatterWorldgenTrees`? — **YES, exclusively.**

The production draw number lives in `scatterWorldgenTrees` (chunks.js:1036, `buildForestTree` at :1061, up to `MAX_WORLDGEN_TREES = 80`/chunk at :1027). **Slice 1 instruments this path and only this path.** A Gary draw-census on the default build (no `?worldgen` flag) must show the `IcosahedronGeometry·240v` + `ConeGeometry·35v` buckets collapse — that is the *only* proof that matters, and it's only producible by touching the v2 path.

### Is v1 `scatterForestTrees` worth touching? — **NO. Park it.**

`scatterForestTrees` (forests.js:831) is reachable only via `?worldgen=0` (chunks.js:408). It is a debug/legacy fallback Gary toggles, not a player-facing path. Touching it:
- moves zero production draws,
- doubles the determinism surface (a second isolated rng stream to gate),
- and the two builders (`buildForestTree`) are **shared** anyway — so the *additive `describe*()` emitters* I build for v2 are automatically available to v1 if it's ever re-promoted. There is no lock-out. **Defer v1 instancing to "if/when `?worldgen=0` is ever the default again," which the `chunks.js:385` stale comment suggests is not the direction of travel.** Critical-path discipline: don't spend a determinism gate on a non-shipping path.

### Is Slice-0 (the tree.js:107 free win) still correct + rng-safe? — **NO. Withdraw it.**

I verified: `tree.js:107` (and `:124`) per-tree `MeshStandardMaterial` lives in `buildTree` (tree.js:96-135), which is called ONLY by `scatterTrees` (chunks.js:1696), which runs ONLY in the v1 `else` branch (chunks.js:447). **It does not execute in v2 production.** My R1 sold it as "a real allocation win on every chunk spawn" — that claim is false for the shipped build. The edit is still *rng-safe in isolation* (it replaces where the material comes from, not the `rng()` pick at `:108`), but a rng-safe edit to dead-in-production code is not a "free win," it's busywork. **There is no separable zero-rng-risk Slice 0 in v2** — the v2 builders already pool materials (`_foliageMats` shared at tree.js:52; `_forestTrunkMat`/`_birchTrunkMat` shared). The only remaining per-spawn cost in v2 is **geometry** allocation (tree.js:163,183,203,215,226,247,264), and pooling geometry across varied-dimension trees IS instancing (unit geo + per-instance scale matrix). So the warm-up slice I wanted doesn't exist; the rng-sensitive work is unavoidably the first real slice.

> If Gary still wants a genuinely-free warm-up commit before the rng-sensitive work, the honest one is **mechanical, not perf**: split the additive `describeForestTree()` emitter into `tree.js` as a pure refactor that the *existing* `buildForestTree` Group path also routes through (single source of truth for rng order), with the golden-hash gate proving byte-identical behavior — zero visual/draw change, but it de-risks Slice 2. ## Tension T1 — gate call: new `bin/test-forest-determinism` vs layout-snapshot + code-review?

**My call: BUILD the golden-hash gate — but make it tiny, and only because layout-snapshot is provably insufficient HERE, not as general policy.**

This is a case where my usual "don't over-build tooling for a hobby game" instinct loses to a verified blind spot. The reasoning, cited:

1. **Layout-snapshot is structurally blind to the exact regression.** Verified: `dumpRegistry()` (main.js:1505-1515) emits no `crown`/`perches`; `normalizeEntries` (bin/layout-snapshot:70-89) diffs only position/footprint/collider/attractor/chunkKey. A foliage size/species/color reorder that leaves trunk *positions* stable passes clean. The Adversary (Vuln 1) is right.

2. **The existing draw-count canary does NOT cover trees.** I checked: `worldgenDrawCounts` is populated only inside `buildWorldgenKind` (chunks.js:1304-1325), which wraps the *cluster* builders (stages/camps/food). `scatterWorldgenTrees` uses its own `rng = mulberry32(worldHash…)` (chunks.js:1039) and is **not** wrapped. So the "positions match but a count moved" safety net (main.js:1520-1522) does not extend to the tree stream. There is no existing canary that catches a tree-rng reorder.

3. **Code-review of rng order is real but not a *gate*.** The Adversary enumerated the exact sequences (5 draws pine, `5+3·bumps` oak, `4+3·crowns` birch, + caller rotation). A human can eyeball that the refactor preserves it — but "a senior dev read it carefully" is not a regression-proof artifact, and the failure mode (every forest regenerates for live players) is the single highest-consequence outcome in this change. Pragmatism says: when the blast radius is "everyone playing across the deploy" and the existing gates are *proven* blind, a one-time ~30-line gate is cheap insurance, not gold-plating.

**BUT — keep it minimal and right-sized for a hobby game:**

- It is **~30 lines**, reusing the exact harness `bin/test-registry-grid` already uses (`register('./node-three-shim.mjs')` per the Adversary): import the real `tree.js`, run `describeForestTree(mulberry32(FIXED))` N times, hash the full descriptor stream (type, trunk dims, greenIdx, every bump/crown draw, rotation), compare to a golden committed from `main`. No WebGL, runs in Codespaces, agent-runnable — which is exactly why it's worth building: it converts the one load-bearing risk from a **Gary round-trip** (my R1 weakness) into an **agent-static gate**. That's a force-multiplier: it lets the agent iterate the descriptor refactor in seconds instead of waiting on Gary to re-capture.
- It only needs to exist **once Slice 1a (descriptor extraction) lands** — because it hashes the descriptor stream, it presupposes the `describe*()` functions. So it's built *as part of* Slice 1a, gating that slice and every slice after.
- I'd **not** gold-plate it into a full forest-placement snapshot (that's what layout-snapshot already does for positions). Descriptor-stream hash for the *visual/foliage* invariant + layout-snapshot for the *position* invariant = complete coverage with minimal new code.

**Net:** layout-snapshot + careful code-review is NOT pragmatically enough here, specifically because both existing canaries are verified-blind to the foliage stream and the consequence is maximal. Build the tiny `bin/test-forest-determinism` golden-hash gate as part of Slice 1a. It's the rare case where building tooling IS the fastest path to a verified result — it moves the load-bearing check off Gary's plate and onto the agent's.
