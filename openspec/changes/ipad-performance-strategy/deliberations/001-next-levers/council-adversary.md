## The Adversary's Order of Operations

**TL/DR:** The iPad evidence says two different things, and the current plan only answers the smaller one. The November 11 far-field fix targets the *stalls* (the 424 ms spikes), but the *steady* 25 to 29 FPS is not explained by JavaScript work at all. On both iPad captures the median frame interval is longer than even the 95th-percentile main-loop work, so a large share of every frame is spent somewhere the capture does not time: Safari's GPU process, draw submission, or a frame-rate cap from the device's power state. The physics engine, which has been on by default since October 30, also runs entirely outside the world and render timers. Before Gary spends another session on the iPad, the capture must be fixed so it can see those three things, and nothing else should land in production so the next run cleanly tests the November 11 fix.

### Priority Sequence

1. **Freeze production performance changes until the next iPad run.** The November 8 fixed-route capture is the only device baseline on the route, and the November 11 far-field change is the only unverified production change since it (`git log`: `c8ce9a1` on 2026-11-11 follows `b222c7a` on 2026-11-09). Landing a second change first turns the next run into an unattributable bundle. The October 22, November 5 and November 6 changes already sit unverified on device (briefing digest; `docs/backlog/performance.md:76`), so the project is one more stacked change away from never being able to say which fix did what.

2. **Repair the capture before spending Gary's device time (capture-only, no gameplay change).** Four blind spots, each cited below in Vulnerabilities:
   - Serialize the far-field job's `applySuperseded` count and the age of the published horizon. Today the capture records `ffCold`, `ffApply` and `ffApplyFrames` (`src/debug.js:2143-2148`) but not `applySuperseded` (`src/farField.js:889`), so a horizon that silently stops publishing would read as a clean win.
   - Time `physicalWorld.advance(...)` (`src/main.js:1288`) and record the fixed steps taken per frame. It runs outside both the world timer (`src/main.js:1789-1793`) and the render timer (`src/main.js:1938-1940`).
   - Report wall-minus-work as a first-class metric per phase, since that gap is where the steady-state frame time actually lives (see the table in Vulnerabilities).
   - Record environment: Low Power Mode on or off, charging state, and the iPad model. The November 7 README admits that battery, thermal and charging state were never supplied (`verification/performance/2026-11-07-ipad/README.md:24-26`).

3. **Do the free attribution on desktop first.** Draw and triangle counts depend on seed, pose and tier rather than on the device (`docs/backlog/performance.md:74` records draws/tris as adaptive-independent), so `__dbg.drawCensus()` (`src/main.js:2691`) can be run at the November 8 route anchors on `?perf=low` without the iPad. The iPad sits at 1,023 to 1,270 median draws and 515k to 628k triangles on Low, against a Low budget of 80 draws and 150k triangles (computed from `baseline-capture.json` samples; budgets in charter Non-Negotiable 6). Desktop can name the owners of those draws, although only the device can price them.

4. **Run one device session as an alternating pair on a single build, not as a series of one-off runs.** Use the same autopilot route as November 8 (`bin/playtest-perf drive --autopilot --world-detail`, `bin/playtest-perf:20-22`), run default, then `physics=0`, then default, then `physics=0`. The default runs verify November 11 against the November 8 baseline, and the pair isolates the cost of physics. `?physics=0` already exists as the legacy path (`DEBUGGING.md:69`), but `bin/playtest-perf` has no way to add it to the capture link (its options are listed at `bin/playtest-perf:12-24`), so a capture-only `--physics off` option is needed. The Auto-versus-Sustained question (`--quality sustained`, `bin/playtest-perf:17`) waits for a second session.

5. **Choose the first real lever only from that session's result:**
   - If physics accounts for most of the unexplained work, the lever is the physics step on Low. That relaxes simulation behavior, which constraint 10 requires to be stated explicitly, so it needs Gary's sign-off as a policy change and not just a tuning change.
   - If wall-minus-work stays large with physics off, the device is waiting on Safari's GPU process and draw submission, and draw reduction is the lever. The cheapest candidate on record is stopping the horizon at the 520 m fog limit, because more than half of the kept Low far-field instances sit beyond it (`verification/performance/2026-11-11-far-field-publication/README.md:103`). It needs Noon and Midnight screenshots because it changes the published set.
   - If the next run shows the far-field indivisible units (14 ms p99, 30.9 ms max on M4, `.../2026-11-11-far-field-publication/README.md:87-92`) still producing visible hitches, split inside `festivalPlan` or the woodland `cellPlan` as that README proposes (`:105`).

6. **Stop doing these:**
   - Tuning the resolution ladder for the iPad. Auto already exhausted it on both captures, and dropping to `pixel-50` did not raise FPS on November 8 (parked 29 before versus 26 after, while draws rose from 1,023 to 1,270). The iPad is therefore paying for a blurry 675×462 image without getting the frames back (`verification/performance/2026-11-07-ipad/README.md:55-61`).
   - Desktop-only structural investigations. The November 7 round ended with no selected rewrite, and Non-Negotiable 9 in the briefing rules out treating desktop results as device results.
   - The "render directly when bloom and Trip are off" candidate, until its shader-program churn is measured (see Vulnerabilities).

### Vulnerabilities Found

-   **The steady frame time is outside the timed code, and the plan is aimed at the timed code.** I took medians per phase from the samples of both iPad captures:

    | Capture / phase | Median FPS | Median wall p50 | Median work p95 | Median draws |
    | --- | ---: | ---: | ---: | ---: |
    | Nov 8 parked | 29 | 32 ms | 22 ms | 1,023 |
    | Nov 8 drive | 25 | 36 ms | 32 ms | 1,025 |
    | Nov 8 parked-after | 26 | 36 ms | 26 ms | 1,270 |
    | Nov 7 parked-after | 40 | 22 ms | 16 ms | 470 |

    The median frame interval exceeds the 95th-percentile JavaScript work in every row, and retained Nov 8 parked frame events show 60 ms walls against 18 ms of work (`verification/performance/2026-11-08-ipad-child-density/baseline-capture.json`, `frameEvents`). The "13 ms outside render and world" in the backlog (`docs/backlog/performance.md:131`) is a real gap, but there is a second and larger gap, between the work and the wall clock, that no current candidate addresses. The CPU render timer only measures command encoding on the page's thread, so 5 to 9 ms there says nothing about what the GPU process does with roughly 1,000 draws. -- Severity: **High**

-   **Physics is unmeasured on the device, and its fixed step makes slow frames slower.** `FixedStepClock` runs 60 Hz steps with up to 5 per call (`src/physics/fixedStep.js:3`), and the frame delta is clamped to 50 ms (`src/main.js:1223`). At 25 FPS that is about 2 steps of Rapier per frame, and at 20 FPS it is 3, so cost rises exactly as frame rate falls. Festival physics became the default on 2026-10-30 (`39e4797`), and physical driving landed on 2026-11-02 (`7e7fd38`), after the October 22 phone run that reached 57 FPS at `pixel-50` (`docs/backlog/performance.md:78`). No iPad capture has ever run without physics, so "the iPad is slow" is confounded with "physics is new." `liveWorld` already tracks `playerResidency.meanStepMs` and `maxStepMs` in `stats()` (`src/physics/liveWorld.js:342`), but the capture never serializes them (the `physical` field in the Nov 8 capture is only the preparation timer inside `worldParts`). -- Severity: **High**

-   **The November 11 fix can look like a win because the work stopped happening, not because it got cheaper.** On Low the far field receives only what is left of a 3 ms streaming wall after landscape, lakes, chunks and physical preparation (`src/perf.js:112`, `src/world.js:125-139`), and a zero remainder plans and publishes nothing that frame (`src/farField.js:899`). On the iPad an ordinary chunk alone takes 31 to 41 ms, so frames that build a chunk leave no remainder at all. Crossing into a new 80 m cell drops the in-flight job (`src/farField.js:887-889`). During sustained driving through new ground on a device roughly three times slower than the M4 (an inference in `.../2026-11-11-far-field-publication/README.md:96`), the horizon can lag or stop publishing for long stretches, and because `applySuperseded` is not serialized (`src/debug.js:2143-2148`) the capture would only show smaller far-field intervals. In the other direction, any positive remainder still runs at least one indivisible unit (`src/farField.js:1010-1022`), so a 30.9 ms M4 unit could become a recurring 90 ms iPad hitch if the threefold inference holds. -- Severity: **High**

-   **Uncontrolled power state can fake or erase a gain.** The November 8 run never exceeded a median of 29 FPS in any phase, and its parked wall p50 was 32 ms. The November 7 run on the same device reached 40 FPS parked. Route and draws differ (470 versus 1,270 parked draws), so this does not prove a cap, but neither capture recorded Low Power Mode, charging or thermal state (`verification/performance/2026-11-07-ipad/README.md:24-26`). If one A/B arm runs with a frame-rate cap and the other without, the comparison is meaningless. Recording the state costs Gary seconds, and losing a session costs him a whole evening. -- Severity: **Medium**

-   **Each extra stacked change multiplies the cost of Gary's device time.** Four production changes now wait on device verification (October 22, November 5, November 6, November 11; briefing digest and `.../2026-11-11-far-field-publication/README.md:9-10`). Gary is the only person who can run the iPad (constraint 11). Every unverified change landed before the next run removes one clean comparison against the November 8 baseline, and the November 8 README itself warns that the older baseline is "attribution context, not an identical-build comparison input" (`verification/performance/2026-11-08-ipad-child-density/README.md:92-94`). -- Severity: **Medium**

-   **"Render directly when bloom and Trip are off" risks shader-program churn on every Auto rung change.** The game renders through a composer whose final `OutputPass` applies the renderer's ACES tone mapping and sRGB output (`src/main.js:302-304,377`). A direct path would only be used on some rungs, so Auto toggling bloom would switch every material between two render paths. Whether that adds new program variants on the first switch must be measured with the `programCount` that the capture already records, before the candidate is scheduled. The project has been burned by exactly this class of failure before: the June light-culler leak drove programs from 54 to 691 (`docs/backlog/performance.md:164-176`). I could not inspect the Three.js r160 program-key source because `node_modules` is not installed here, so this is a required gate rather than an established defect. -- Severity: **Medium**

-   **Deferred chunk disposal is an iPad memory risk.** The "budget chunk unloads" candidate (`docs/backlog/performance.md:128`) would move dispose walks behind a budget. Under sustained driving, where streaming already uses up the 3 ms wall, the backlog of undisposed GPU buffers could grow without bound, and iPad Safari terminates tabs under memory pressure rather than slowing down. If this candidate is ever pursued it needs a hard cap on the backlog (dispose synchronously past N pending) and a `geo`/`tex`/`heapMB` trend in the capture, which the samples already carry. Registry and collider removal must stay immediate, as the backlog notes (Non-Negotiables 4 and 5). -- Severity: **Low** (only matters if the candidate is chosen)

-   **Freezing static chunk subtrees can silently stop moving content.** The candidate requires `scene.matrixAutoUpdate = false` (`docs/backlog/performance.md:127`), and chunk groups now contain physics-driven props such as camp chairs that move via instance transforms (`docs/backlog/performance.md:112`) plus nightness-polled animated parts (AGENTS.md constraint 8). A wrong freeze produces frozen props with no error and no stall, and the defect surfaces only in a full game boot with physics on. The measured ceiling is about 5% of sampled desktop CPU, which makes this a poor bet before the 13 ms gap is attributed. -- Severity: **Low**

### Verdict

-   **Verdict**: Proceed with mitigations
-   **Key Concern**: The next iPad session will be wasted if it runs on the current capture, because the capture cannot see where the steady-state frame time goes (wall-minus-work, physics stepping) and cannot tell a cheaper far-field horizon apart from one that silently stopped publishing.
-   **Recommendation**: First freeze production changes. Then add capture-only instrumentation for physics step time and steps per frame, far-field supersession and horizon age, wall-minus-work, and power state, plus a capture-only `physics=0` option in `bin/playtest-perf`. Do the draw census on desktop at no device cost. Then spend one Gary session on an ABAB pair (default versus `physics=0`) on the November 8 route. Only after that should the first lever be picked: the physics step on Low (an explicit simulation-policy relaxation needing Gary's sign-off) or draw reduction starting with the fog-limit horizon cut. Stop tuning the resolution ladder for the iPad.
-   **The "Killer" Finding**: On every iPad phase the median frame interval exceeds the 95th-percentile JavaScript work, for example 32 ms against 22 ms parked on November 8. Rapier physics, which became the default after the last fast phone measurement, runs entirely outside the world and render timers (`src/main.js:1288` versus `1789-1793` and `1938-1940`). Neither has ever been measured on the iPad, and both are untouched by the far-field work that the current plan centers on.
-   **Risk Level**: High

## Round 2 — Reactions

**TL/DR:** I was wrong about the main thing. The Profiler and the Maverick read my own numbers correctly and I did not: a frame that needs 22 ms of main-thread work on a 60 Hz display waits for the next refresh and shows up as a 33 ms interval, so the gap I called "time outside the timed code" is mostly waiting for the screen to refresh, and I withdraw the GPU-process framing. I hold my position on three points, which are freezing production changes, making the far-field supersession visible, and timing physics. I add two points that every other persona missed. The first is that a single Auto run cannot "accept" the October 22, November 5 and November 6 changes, because the November 8 baseline already contained them. The second is that no iPad run has ever been repeated, so nobody knows how much the same route varies from run to run on this device.

### Concessions

-   **Profiler, "Evidence base" item 1, and Maverick, Priority 1 ("Frames of 22 to 27 ms cannot fit a 16.7 ms vsync, so they settle at about two vsyncs").** They are right, and my Round 1 lead finding misread the same table. If the work for a frame is 22 ms, a 60 Hz `requestAnimationFrame` loop cannot show that frame until the second refresh, so a 32 to 36 ms median interval is exactly what main-thread-bound frames look like. The only phase with work p95 below 16.7 ms, November 7 parked-after at 16 ms, is also the only one whose median interval drops to 22 ms, which is a mix of one-refresh and two-refresh frames. That fits refresh rounding and does not need a hidden GPU cost. The 60 ms walls against 18 ms of work that I cited come from retained `frameEvents`, which keep only slow frames, so they are outliers chosen for being slow and say little about the typical frame. I withdraw "the steady frame time is outside the timed code" as a finding. The supported statement is narrower: the steady cost is main-thread work of about 20 to 26 ms, and roughly 12 to 15 ms of it is untimed. A GPU share is not ruled out, because Safari gives no GPU timer, but it is no longer the leading hypothesis.
-   **Maverick, Priority 3, on Auto's trigger.** I verified it. `DROP_FRAME_MS = 22` and `DROP_P95_MS = 33` (`src/adaptiveQuality.js:50,52`), so a device locked to the two-refresh rate averages about 33 ms per frame and always trips the drop rule. Auto is therefore built to fall to its lowest rung on any device where the main thread is the limit, whatever resolution would actually cost. That is a sharper version of my "stop tuning the resolution ladder" point, and the Maverick deserves the credit for it.
-   **Profiler, Evidence item 3, and Architect, Priority 1, on the localhost-gated tracer.** Verified at `src/main.js:95-100`. `peopleFrameTrace` and `peopleBaseline` only run on `localhost` or `127.0.0.1`, so the backlog's method of "a people-frame trace on the device" (`docs/backlog/performance.md:131`) cannot work on a phone or iPad connecting over the LAN. I had missed this, and it is the strongest argument for coarse capture-gated section timers over any reuse of the existing tracer.
-   **On my `physics=0` ABAB pair.** Three personas propose timing physics as one section among several (Profiler Priority 1, Architect Priority 1, Pragmatist Priority 1). A section timer around `physicalWorld.advance` answers "how much does the step cost" without spending a whole device run on it, so I drop the dedicated `physics=0` arms from the first session. I keep one caveat, which is that physics also hooks the render path at `physicalWorld.beginRender()` (`src/main.js:1906`) and `endRender()` (`src/main.js:1942`), outside the render timer's 1938-1940 window. The section timer has to cover those calls too, or the physics share will be undercounted.
-   **Power state.** Refresh rounding explains the November 8 run's sub-30 medians without a Low Power Mode cap, so I downgrade that risk from Medium to Low. I still want the state written down, because it costs seconds to record and could make one comparison meaningless.

### Rebuttals

-   **Pragmatist, Priority 2 ("This single run also covers the Oct 22, Nov 5 and Nov 6 'still awaiting device verification' bullets"), Architect, Priority 2, and Maverick, Priority 2 ("Auto ... simultaneously serves as the device acceptance run for the November 11 far-field fix, November 6 terrain, November 5 child pooling and October 22 registry work").** This is factually wrong. The November 8 baseline build was served from head `5e85a2d` (which already contains `65c0085`, the November 5 work), with uncommitted edits including `src/worldgen/terrain.js` and `src/world.js` (`verification/performance/2026-11-08-ipad-child-density/baseline-snapshot.json`, fields `head` and `dirty`). The November 7 README likewise says its build "includes the existing uncommitted November 6 terrain work" (`verification/performance/2026-11-07-ipad/README.md:31`). Between `b222c7a` and `c8ce9a1` the only `src` changes are `farField.js`, `terrain.js`, `woodlandCamping.js`, and small edits to `debug.js` and `main.js` (`git diff --stat b222c7a c8ce9a1 -- src`). A new Auto run compared with November 8 therefore measures November 11 and nothing else. It cannot "accept" the earlier three, because every iPad capture on record already included them, so no device "before" exists for them. If Gary trims those ROADMAP bullets on the strength of the next run, the project will record an acceptance that never took place. The honest options are to mark those three as "present in every iPad capture, no device before/after exists" or to build an explicit revert build, and I recommend the first because it costs nothing.
-   **Pragmatist, Priority 3 ("Far-field tail gone (worst driving world interval below roughly 50 ms): close the far-field item"), and Architect, Structural Risks ("read `ffApplyFrames` and the time to the first horizon").** Neither check catches the failure I raised in Round 1. `applyFrames` is only written when a job completes (`src/farField.js:923`), and a job that gets dropped on a cell crossing increments `applySuperseded` (`src/farField.js:889`), which the capture does not serialize (`src/debug.js:2143-2148`). Time-to-first-horizon measures boot and says nothing about whether the horizon keeps updating while the car drives. A small worst far-field interval combined with a horizon that rarely publishes would pass the Pragmatist's decision table exactly as written. The decision rule needs a second condition: at least one publication completed per N cells crossed, with zero long stretches of supersessions in a row. Without that condition, "tail gone" could close the item on the strength of work that simply stopped running.
-   **Profiler, Priority 2, and Maverick, Priority 2: three different runs, one of each.** There is a hidden assumption here that one run per arm is enough. No route has ever been repeated on the iPad. The two existing captures differ in route, and draws moved from 469 to 1,270 across poses inside a single build (Profiler's own table), so how much the fixed route varies on this device is unknown. If arm (a) and arm (b) differ by 3 FPS, nobody can say whether that is the change or ordinary run-to-run variation. The cheapest fix is to put the Auto run first and last (Auto, X, Y, Auto). That adds about two minutes and turns the session into something that can be compared, and the November 8 README itself asked for "alternating repeats before claiming a population benefit" (`verification/performance/2026-11-08-ipad-child-density/README.md:92-94`).
-   **Profiler, Priority 2(c), and Maverick, Priority 2: the `farField=0` run.** `bin/playtest-perf` has no option for adding arbitrary URL flags. Its options are scenario, desktop, browser, no-open, tier, quality, seed, autopilot, child-cohort, world-detail, port and no-qr (`bin/playtest-perf:12-24`). A `farField=0` arm therefore needs a small tooling change before the session, just as my `physics=0` option did. It is not a blocker, but it belongs on the prep list, because otherwise Gary would have to edit a URL by hand on the iPad, and a hand-edited link is easy to get wrong.
-   **Pragmatist, Priority 4b, and Architect, Priority 4 ("render directly when bloom and Trip are both off" as a render-CPU option).** Once the device is understood to be main-thread-bound, this candidate mostly saves full-screen GPU passes at 675×462. The Profiler (Priority 7) and the Maverick ("What to stop doing") both say the same. The CPU saving is a handful of pass draws against roughly 1,000 scene draws. Its tone-mapping risk has not been measured, and neither has my program-count risk. I would keep it parked for the iPad, not ranked second.
-   **Maverick, Priority 4: freezing static chunk subtrees as the next code target.** I still disagree on the order, for two reasons. The evidence for it is a desktop profile row, and the Maverick concedes that the iPad payoff "is a hypothesis." More importantly, chunk groups now contain physics-adopted props, and the physics hooks write render transforms around the render pass (`src/main.js:1906,1942`). A frozen branch that holds a physically moving prop fails silently, with no error and no stall. The Maverick asks for a "nothing animated lives in a frozen subtree" check, which is the right instinct, but that check must include physics-adopted instances and nightness-polled parts, and it only makes sense after the device split shows matrix updates as a meaningful share.
-   **Maverick, Alternative Approach (staggered updates for distant actors with a doubled `dt`).** The Maverick openly flags the determinism and constraint-10 risks, and I credit that. The specific hazard is that a doubled `dt` on alternating frames changes collision outcomes for crowd members that physics or the player can touch, and crowd steering already uses parity tiebreaks (CHANGELOG, "idx-parity tiebreak"). Behavior that depends on the frame count would then also depend on frame rate, so two players on different devices would see different crowd results. This is not a blocker for exploring the idea, but it needs a determinism test that runs the same seed at 30 and 60 FPS before anyone designs it.

### Sharpened points

-   **Profiler, "Things to stop doing" ("Use work p95 against 16.7 ms as the iPad's real budget line").** I agree, and I would add a warning that follows from it. Because of refresh rounding, any lever that cuts parked work from 22 ms to 18 ms will show **zero** FPS change. The acceptance metric for the step-by-step levers therefore has to be work p95, not FPS. Otherwise a real 4 ms win will be rejected as "no detectable change," which is the same verdict that closed the November 5 and November 6 desktop passes (Pragmatist, Deferred/Cut). This also means the November 7 "nomination threshold" rejections should be re-read in terms of work rather than FPS before anyone treats them as final for the iPad.
-   **Pragmatist, Slice 2 (fog-limit cull "behind a URL/tier flag ... default-off until the iPad A/B shows draw or frame gain").** I agree, and this is the right shape for every candidate on the iPad. A default-off flag means the production Pages deployment stays identical to the November 8 baseline build until the device has spoken, which satisfies my freeze without stalling desktop work.
-   **Architect, Structural Risks (no far-field capability spec; `world-streaming` still says terrain is flat).** I agree. It also explains why the supersession behavior went untested: no requirement says "the horizon must publish within N cells while driving," so the November 11 change had no contract to check its starvation case against.
