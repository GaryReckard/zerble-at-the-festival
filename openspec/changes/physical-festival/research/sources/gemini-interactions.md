# **Architecture for Hybrid Physical Interactions in a Streaming WebGL Environment**

## **Architectural Paradigm and Structural Overview**

Integrating dynamic, localized physical interactions into a procedurally generated, chunk-based Three.js browser game requires reconciling fundamental computational conflicts. The game environment, characterized by an outdoor music festival navigated by an arcade-style cart named Zerble, relies on high-performance rendering techniques to sustain target framerates on constrained mobile devices. The primary mechanism for this performance is instanced rendering, which delegates the drawing of thousands of identical static props—such as camp chairs, coolers, and cups—to a single GPU draw call. However, applying rigid-body physics to these objects inherently demands individual transformation matrices, unique bounding volumes, and active continuous collision detection. Permanently converting the entire procedural world into active dynamic bodies would invariably exhaust the computational budget and memory quotas of mobile browsers.  
The architectural paradigm proposed to resolve this conflict is Bounded Ephemeral Physics. Under this framework, the vast majority of the procedural world remains entirely static and economically rendered via instanced geometries. Physics processing, along with distinct logical object identities, is strictly instantiated on a just-in-time basis. When a collision threshold is breached by a dynamic entity, the targeted prop transitions seamlessly from a static instanced array into an active rigid body, temporarily participating in the physical simulation before eventually settling and returning to an instanced, dormant state.  
This report details the implementation of this architecture, strictly adhering to a no-build, browser-module workflow. The design incorporates high-performance WebAssembly (WASM) physics, additive animation blending for non-player character (NPC) reactions, explicit ownership hierarchies for composite objects, and a chunk-streaming lifecycle that gracefully handles object persistence and safe distance resets without accumulating permanent memory overhead. The subsequent sections investigate engine selection, rendering synchronization, memory invariants, interaction systems, and a concrete interaction sequence to validate the proposed architecture.

## **Physics Engine Selection and Mobile Memory Invariants**

The requirement to utilize a no-build, browser-module/import-map workflow places immediate constraints on the selection of a physics engine. Historically, this constraint favored pure JavaScript physics engines, such as the widely utilized cannon-es package. As a pure JavaScript port, cannon-es avoids compilation steps and integrates seamlessly into simple HTML setups1. However, performance benchmarks and architectural trends demonstrate that cannon-es suffers from significant performance degradation when managing more than a few hundred active bodies, primarily due to its brute-force broadphase and pure JavaScript constraint solver3.  
Given the necessity to support cascading chain reactions and multi-body interactions (such as a chair striking a cooler, which in turn ejects a cup), the performance mandate strictly requires a WebAssembly-backed engine. The @dimforge/rapier3d-compat package emerges as the verified solution. This specific distribution of the Rapier physics engine embeds the compiled WASM binary as a Base64 string directly within an ECMAScript Module (ESM). Consequently, it natively circumvents the need for bundlers like Webpack or Vite, operating flawlessly over a standard content delivery network (CDN) via an import map5. Rapier provides SIMD-accelerated calculations, robust continuous collision detection (CCD), and the capacity to manage thousands of active bodies while maintaining 60 frames per second on mobile hardware4.  
Deploying WASM-based physics within a mobile browser, specifically iOS Safari, introduces severe memory management challenges. WebKit, the underlying engine for Safari, imposes aggressive memory quotas on the WebContent process. Depending on the device iteration and total system RAM, a single origin may be capped between 1.5 GB and 2 GB8. WebAssembly linear memory presents a distinct architectural hazard: it possesses the capability to grow via the memory.grow operation, but it lacks the capability to shrink or return allocated memory to the host operating system9. If the physics architecture dynamically creates and destroys rigid bodies indiscriminately, the WASM heap will monotonically expand until the iOS operating system forcefully terminates the browser tab with an Out-Of-Memory (OOM) exception11.  
To guarantee Safari and iOS compatibility, the architecture must enforce strict Object Pooling. At application initialization, the system must allocate a fixed pool of Rapier RigidBody and Collider instances. When a procedural prop is struck and becomes dynamic, it does not instantiate a new body; instead, it claims a dormant body from the pre-allocated pool, reconfigures its physical properties (mass, shape, restitution), and updates its transform. When the object eventually settles and is removed from the active simulation, its velocity is zeroed, it is relocated to a hidden coordinate (e.g., a Y-axis value of \-1000), and it is returned to the pool12. If runtime allocation proves absolutely necessary for rare edge cases, the architecture must explicitly invoke Rapier's manual memory management methods, such as world.free(), to ensure the WASM linear memory boundaries are respected and resources are properly dereferenced14.

## **Rendering Synchronization and the Instancing Swap Pattern**

The visual representation of the festival environment relies on THREE.InstancedMesh to render repetitive static props. This allows the GPU to render thousands of identical objects, such as camp chairs, using a single geometry, a single material, and an array of transformation matrices, resulting in precisely one draw call per prop type15. The architectural challenge arises when an individual instance within this array must detach and become a uniquely simulated physical body.  
Recent additions to the Three.js ecosystem, such as THREE.BatchedMesh, permit the batching of varying geometries into a single draw call and offer built-in visibility toggling. However, profiling reveals that BatchedMesh incurs substantial CPU overhead due to its per-frame frustum culling and sorting operations, frequently resulting in CPU bottlenecks that degrade performance to unacceptable levels on mobile devices (e.g., dropping to 20-30 FPS under heavy load)17. Therefore, InstancedMesh remains the optimal choice for massive, homogenous arrays of static props, necessitating a custom, low-overhead mechanism to transition objects from static instances to dynamic meshes.  
The most performant mechanism for this transition is the ![][image1] Matrix Swap-and-Decrement pattern. Modifying an instance's scale to zero in order to hide it forces the GPU to unnecessarily process degenerate matrices and frequently corrupts lighting calculations18. Instead, the architecture must manipulate the active count of the instanced array.  
When an impact event signals that a specific chair must become dynamic, the system performs a sequence of constant-time operations. First, it retrieves the transformation matrix of the targeted instance using instancedMesh.getMatrixAt(targetIndex, tempMatrix)20. Next, it retrieves the matrix of the final active instance in the array using the current count property. The system then writes this final matrix into the slot of the targeted instance, effectively overwriting it. The total active count of the InstancedMesh is then decremented by one, and the instanceMatrix.needsUpdate flag is set to true22. Simultaneously, a standalone THREE.Mesh is pulled from a rendering object pool, positioned using the retrieved tempMatrix, and functionally bound to an activated Rapier rigid body.  
This swap operation executes in constant time, entirely bypassing GPU processing for the hidden instance. When the dynamic rigid body eventually reaches a sleeping state, the process is inverted. The InstancedMesh count is incremented, the resting transformation matrix of the dynamic mesh is written into the newly available index at the end of the array, and the dynamic THREE.Mesh and physics body are returned to their respective pools.  
A critical invariant must be observed during this process. Three.js performs frustum culling for an InstancedMesh based on a singular, global bounding sphere. Modifying matrices within the array or injecting new matrices during procedural chunk generation can invalidate these bounds, causing the entire array to flicker or disappear when the camera pans25. The architecture must ensure that instancedMesh.computeBoundingSphere() is explicitly re-evaluated whenever the array undergoes significant spatial modification, or alternatively, frustum culling must be disabled locally for highly volatile arrays27.  
Furthermore, Three.js does not automatically garbage-collect GPU resources. If dynamic meshes or materials are created and discarded rather than pooled, they will remain resident in Video RAM (VRAM) until the browser crashes16. The architecture dictates that if a mesh or material must be permanently removed, developers must explicitly call geometry.dispose() and material.dispose(). This explicit disposal is non-negotiable for maintaining the long-term stability of the application29.

## **Authored Additive Animation versus Rigid Body Simulation**

The interaction design dictates that occupied camp chairs present a nuanced physical challenge: the NPC seated in the chair must react dynamically—bracing, losing balance, falling out, and recovering—while the chair itself moves independently. Implementing a fully constrained physical ragdoll for every NPC (where each limb operates as a separate rigid body connected by complex joint motors) introduces uncontrolled computational complexity, severely impacts the physics step time, and is notoriously difficult to tune for subtle, expressive reactions.  
The architecture resolves this by strictly separating the rigid body simulation of the inanimate prop from the authored skeletal animation of the character. Real rigid-body physics is reserved exclusively for inanimate objects like chairs, coolers, and cups, where the simulation provides chaotic, emergent gameplay. For living characters, the system employs additive animation blending via the THREE.AnimationMixer to simulate physical reactions predictably and expressively.  
When the player's cart clips an occupied chair, the Rapier physics engine processes the collision and calculates the resulting impulse. If this impulse falls below a predefined ejection threshold, the NPC remains kinematically attached to the chair. To simulate the impact, the architecture triggers a procedural wobble using an additive animation clip. An animator authors a specific "brace and flail" animation sequence in external software. Upon loading this sequence into Three.js, the architecture utilizes THREE.AnimationUtils.makeClipAdditive(clip). This utility processes the keyframe tracks, subtracting the pose values at the initial reference frame from all subsequent frames, converting absolute bone rotations into relative mathematical deltas31.  
The resulting AnimationAction is assigned THREE.AdditiveAnimationBlendMode. During a low-velocity impact, this additive action is played simultaneously with the NPC's base animation (e.g., sitting and drinking). The magnitude of the physical impulse is translated into an animation weight via the action.setEffectiveWeight(impactForce) method34. This applies a procedural, mathematically scaled displacement to the character's spine and arms, creating a convincing reaction that layers seamlessly over their current activity, completely circumventing the cost of a physics solver.  
If the collision impulse exceeds the critical ejection threshold, the additive wobble is insufficient. The architecture initiates a state transition to eject the character. The NPC's root node is immediately detached from the chair's transformation hierarchy. The NPC's central character collider transitions from a static sensor into a kinematic rigid body, and a ballistic trajectory is calculated based on a fraction of the impact velocity. The AnimationMixer crossfades from the sitting animation to a tumbling animation. Once the kinematic body detects a collision with the ground plane (the navigation mesh), the trajectory terminates, a recovery animation (standing up) plays, and the NPC seamlessly re-enters its standard procedural navigation state machine. This hybrid approach guarantees expressive, believable interactions without the catastrophic physics glitches associated with constrained ragdolls clipping through terrain.

## **Kinematic Ownership and Attachment Hierarchies**

Physical interactions involving composite objects, such as a cup resting in a cooler's cupholder or a lid attached to a cooler body, require explicit ownership graphs and detachment rules. The architecture distinguishes between tightly coupled articulated constraints and loosely coupled kinematic synchronizations.

| :---- | :---- | :---- | :---- |
| **Occupied Chair** | Procedural World | Instanced Static | Collision impulse \> ![][image2] |
| **Cooler Base** | Procedural World | Instanced Static | Collision impulse \> ![][image3] |
| **Cooler Lid** | Cooler Base | Revolute Joint Constraint | Cooler impulse \> ![][image2] |
| **NPC Held Cup** | NPC Hand Bone | Transform Parented | NPC Ejection OR Impulse \> ![][image4] |
| **Resting Cup** | Cooler Base / Chair | Kinematic Transform Sync | Host acceleration delta \> ![][image5] |

Articulated objects, such as the cooler lid, warrant genuine physics constraints. When a cooler is activated from the instanced array, the physics pool yields two separate rigid bodies (base and lid) connected by a Rapier RevoluteImpulseJoint7. This allows the lid to swing open dynamically when the cooler tumbles.  
Conversely, simulating a light cup resting on a heavy cooler using physical friction or a breakable fixed joint forces the physics solver to reconcile extreme mass ratios, frequently resulting in simulation jitter and instability. The architecture dictates that resting objects utilize manual kinematic synchronization. While the cup sits in the cupholder, it does not exist as an independent rigid body. Its visual representation is simply parented to the cooler's transform. During the main game loop, prior to stepping the physics world, the system evaluates the acceleration delta of the cooler body. If the acceleration exceeds the predefined ![][image5], the cup's attachment state transitions to free. The system instantiates a dynamic rigid body for the cup from the pool, applies the cooler's instantaneous velocity vector compounded with a minor, randomized upward impulse, and detaches the visual mesh. This guarantees smooth detachment without taxing the constraint solver.  
To detect the initial collisions that trigger these events, the architecture relies on Rapier's active event system. Colliders associated with interactive props are initialized with the ActiveEvents::COLLISION\_EVENTS flag35. The physics pipeline generates an event queue during each step. The main application thread drains this queue, evaluates the magnitude of intersecting forces, and dispatches the necessary matrix swaps, additive animations, and hierarchical detachments based on the rules defined in the ownership matrix.

## **Stable Object Identity, World Streaming, and Floating Origins**

The procedural generation of the outdoor festival involves streaming chunks of the world in and out based on the player's proximity. This introduces a severe lifecycle challenge: reconciling displaced dynamic objects with the deterministic nature of procedural generation. If an object is moved, its new state must not inherently corrupt the procedural seed, nor should the system require a permanently expanding database to track the location of every bumped chair.  
The architecture leverages Ephemeral State Identity to handle distance resets gracefully, splitting dynamic objects into two distinct pools: the Local Dynamic Pool and the Global Dynamic Pool.  
When a procedural chunk loads, it executes a deterministic noise function, populating the static InstancedMesh arrays for chairs, coolers, and cups. The chunk possesses zero awareness of the physics system. When the player strikes a chair, it is swapped out of the instanced array and enters the Local Dynamic Pool associated with that specific chunk. If the player drives away and the chunk crosses the distance threshold for unloading, the chunk manager destroys the InstancedMesh buffers and aggressively reclaims all entities within that chunk's Local Dynamic Pool. The displaced chair is returned to the physics pool and visually despawns.  
However, if the player picks up a cup or pushes a cooler along with their cart, moving it across a chunk boundary, the object's tracking tag shifts from the Local Dynamic Pool to the Global Dynamic Pool. Entities in the Global Dynamic Pool are immune to chunk unloading events and persist visually and physically in the player's immediate vicinity.  
A critical invariant is the Safe Distance Reset. If a Global Dynamic object is abandoned by the player (e.g., dropped on the ground) and falls outside the active viewing frustum and interaction radius for a specific time threshold (e.g., 30 seconds), the garbage collection sweep forcefully returns it to the physics pool. This aggressive purging guarantees a flat memory curve over prolonged play sessions.  
If the player returns to the original campsite chunk, the deterministic procedural generator will blindly spawn a brand-new instanced cup, chair, and cooler in their exact original positions. Because the architecture abandons the requirement for permanent historical persistence, it entirely sidesteps the catastrophic memory leaks and serialization complexities of tracking arbitrary prop permutations. In an arcade-style environment, the occasional duplication of a carried cup upon returning to a spawn point is an acceptable aesthetic trade-off for absolute architectural stability and infinite memory safety.  
Furthermore, infinitely procedural worlds inevitably encounter floating-point precision degradation. As the player travels vast distances from the initial coordinate origin (0,0,0), the 32-bit floats used by WebGL and Rapier begin to lose precision, causing models to jitter and physics to tunnel through geometry37. To combat this, the architecture implements a Floating Origin shift. When the camera exceeds a predefined distance threshold, the entire world is mathematically teleported back toward the origin. Rapier physics bodies do not automatically inherit this shift. When a floating origin shift is triggered, the architecture must iterate through all active dynamic bodies in the pool and manually adjust their transforms via body.setTranslation() relative to the origin delta39. To prevent the physics engine from interpreting this teleportation as massive instantaneous velocity (which would cause extreme tunneling and collisions), continuous collision detection (CCD) and physics integration must be paused for the exact frame the shift occurs.

## **Dynamic Navigation and Gameplay Collision Alignment**

Displaced objects must fundamentally alter the gameplay space; a cooler knocked into a pathway must disrupt NPC pathfinding. The NPCs utilize recast-navigation-js for movement. However, rebuilding an entire static navigation mesh (NavMesh) at runtime to accommodate a moving cooler is prohibitively slow and will cause the main thread to stall40.  
The architecture must exclusively employ the Detour TileCache API, which is explicitly engineered for semi-dynamic environments40. The integration of physical displacement with pathfinding operates as follows:  
When a large object, such as a cooler or a flattened direction sign, settles into a resting state, the game logic calculates its axis-aligned bounding box or cylinder radius. It then dispatches an obstacle request to the Recast instance using tileCache.addBoxObstacle() or tileCache.addCylinderObstacle()40. The NavMesh does not update instantaneously. The main game loop must iteratively call tileCache.update(navMesh) until the returned upToDate flag evaluates to true40. To prevent this operation from stuttering the main thread, the Recast TileCache update cycle should be offloaded to a Web Worker, passing the obstacle coordinates via post-message and receiving the updated navigation polygons asynchronously42.  
A critical failure case must be managed regarding obstacle limits. The TileCache architecture supports a maximum queue of exactly 64 concurrent obstacle requests. Exceeding this limit forces the engine to throw a DT\_BUFFER\_TOO\_SMALL error, silently failing to register the obstacle40. To enforce the Obstacle Limit Invariant, minor dynamic props (such as cups or sliding chairs) are strictly prohibited from registering as NavMesh obstacles. Only major path-blockers (coolers, large signs) may request a tile cache update.  
Direction signs that bend, flatten, or fall over present an opportunity to favor authored animation over rigid-body physics. A sign anchored to the ground does not require full physical simulation. It can be implemented as a THREE.SkinnedMesh featuring a single bone at its base. When Zerble impacts the sign, the collision normal is calculated, and a procedural rotation is applied to the bone, angling it away from the impact vector. A TileCache obstacle is then registered at the flattened location. This methodology guarantees the sign remains anchored and visually damaged without engaging the physics solver, maximizing performance. When the sign eventually falls out of the active neighborhood radius, the garbage collection sweep resets the bone rotation and removes the NavMesh obstacle, reverting the sign to its pristine procedural state.

## **Incremental Implementation Sequence and Milestones**

To prevent uncontrolled complexity and event cascades, the development of this architecture must proceed through strictly isolated, independently testable milestones.  
**Milestone 1: The O(1) Matrix Swap Foundation.** The objective is to validate the rendering transition without any physics overhead. A developer clicks a static instanced cube. The logic swaps the targeted matrix with the final array index, decrements the count, updates the buffer, and spawns a standalone THREE.Mesh at the extracted coordinates. Clicking again reverses the process. Success is defined by seamless visual continuity without generating new memory allocations.  
**Milestone 2: ESM Physics Pooling.** Integrate @dimforge/rapier3d-compat via the import map. Pre-allocate an array of 500 rigid bodies. Drop them into the scene. When their linear and angular velocities fall below the sleep threshold, they must automatically relocate to the hidden Y-coordinate and return to the pool array. Success is defined by monitoring renderer.info.memory and the browser heap snapshot to ensure zero new WASM memory is allocated during the recycling phase.  
**Milestone 3: Kinematic Detachment.** Establish the ownership hierarchy. Lock a cup kinematically to a moving cooler. Apply a sudden impulse to the cooler. The code must accurately detect the acceleration threshold, sever the transform parent, claim a dynamic body for the cup, and assign it the correct inherited velocity vector.  
**Milestone 4: Additive Reaction Blending.** Load an NPC with a looping idle animation. Extract a single frame from an authored impact clip to establish the reference frame. Execute makeClipAdditive. Programmatically trigger varying impact forces and validate that the NPC spine and arms wobble proportionally without interrupting the underlying idle loop.  
**Milestone 5: Asynchronous TileCache Updates.** Initialize recast-navigation-js within a Web Worker. Spawn an NPC navigating a pre-calculated path. Drop a dynamic cooler directly into the path. The main thread calculates the bounding box and posts the addBoxObstacle request to the worker. Success is defined by the worker returning the updated polygon data and the NPC dynamically calculating a new route around the cooler, with zero frame drops on the main render thread.  
**Milestone 6: Ephemeral Streaming Identity.** Carry a dynamic prop across a procedural chunk boundary. Force the origin chunk to unload. Validate that the prop survives the Local-to-Global pool migration. Return to the origin coordinates and verify the chunk regenerates deterministically without throwing null reference exceptions related to the missing prop.

## **Explicit Invariants and the Argument Against Overengineering**

The structural integrity of this architecture relies on adhering to explicit invariants. The Memory Allocation Invariant dictates that dynamic rigid bodies and meshes must never be instantiated with the new keyword during gameplay; they must always be claimed from pre-allocated pools to prevent GC stutters and WASM OOM crashes. The Obstacle Limit Invariant restricts TileCache requests strictly to major path-blocking entities to prevent exceeding the hardcoded 64-request queue. The Frustum Culling Invariant requires explicit bounding sphere recalculation whenever instanced arrays are significantly modified.  
The strongest argument against deviating from this design—specifically, the temptation to overengineer a system that attempts to maintain permanent global state synchronization—is the inevitability of cascading state corruption and memory bloat. If the architecture attempted to serialize the exact position, rotation, and kinematic constraint status of every displaced cup and cooler to a permanent database, the payload for loading a chunk would grow infinitely as the player explores.  
Re-injecting dynamic, saved states back into a purely mathematical, noise-driven procedural generator creates catastrophic edge cases where static procedural terrain might intersect with saved dynamic props, causing physical explosions upon load. Managing the exact deserialization lifecycle of a cooler with a half-open lid and a detached cup hovering nearby requires massive, error-prone logic that provides negligible gameplay value.  
By actively embracing the arcade nature of the experience and treating objects as ephemeral entities that reset to their procedural origins once abandoned, the architecture guarantees a flat memory curve, constant framerates, and absolute procedural stability. The illusion of a persistent physical world is maintained perfectly within the player's immediate radius, efficiently delivering the playful, varied physical interactions required by the design without compromising the strict limitations of the mobile web environment.
