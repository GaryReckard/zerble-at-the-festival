# Physics Engine and Rendering Architecture

For performance and determinism, use a modern WASM engine like **Rapier** (Rust-based) over Ammo.js or Cannon/Oimo. Rapier is explicitly designed for real-time game physics (rigid bodies, joints, cloth, etc.), has SIMD/parallel optimizations, and its WASM builds are cross-platform deterministic. By contrast, older JS engines (Cannon.js, Oimo.js) lack WASM acceleration and are unmaintained. (Ammo.js/Bullet can simulate complex scenes, but has higher memory and CPU costs on web.) Thus we recommend Rapier via its JS/WASM binding. Rapier supports joints (hinges for cooler lids, fixed/joint constraints) and even soft bodies, which enables articulated objects and cloth-like effects (e.g. bending signs).

Render static props with **InstancedMesh** for efficiency, adding physics bodies only on-demand. When a prop becomes “active” (e.g. a collision occurs), remove it from the instanced set and create a separate mesh+body with its own transform. Three.js’s AmmoPhysics integration shows how instanced meshes map to many bodies (one per instance). Here, we do the reverse: use instancing for static props, and spawn individual meshes for dynamic ones. When spawning, copy the instanced transform matrix to a new Mesh, attach a Rapier rigid body, and optionally link joints (e.g. cupholder constraints). After activation, the instanced mesh’s `count` is decremented (using the swap-with-last trick) so the removed instance no longer renders.

# Occupied Chairs and NPC Reactions

**Chairs:** We treat an empty chair’s physics as a simple rigid body (e.g. convex hull). If **occupied**, simulate the chair but handle the person via animation/IK and simple colliders. On light impacts, play a *bracing* animation on the occupant (leaning away or gripping), without detaching. For stronger collisions, detach or “eject” the occupant. Rather than a full ragdoll (very expensive), use a *brief active-ragdoll* sequence: switch the skeleton to physics for a few frames or play a canned “fall out of chair” animation with randomized variance. (Rapier can simulate a ragdoll via joints, but doing so continuously for every person is too costly; use it only for one shot and blend back to keyframed animations). For example, if chair velocity exceeds a threshold, spawn a temporary physics body or skeleton colliders on the pelvis/torso, apply impulse, then after a short time blend back to standing with a “get-up” animation. This hybrid approach mimics active-ragdoll techniques (common in games) without always simulating limbs. 

**NPC collisions:** Give each NPC a root physics proxy (a capsule or box) mainly for quick collision response. On low-speed bumps, just slide the root or play a “stumble” blend animation. On higher-speed impacts, briefly enable partial physics on the upper body: e.g. attach a small ragdoll on hips/torso for 0.5–1s to allow a natural recoil, then back to animation. For navigation, remain kinematic—don’t replace NPCs with fully dynamic rigid characters. By tuning thresholds, most minor collisions use fixed/animated reactions, and only edge cases spawn a short-lived physics effect. (This yields expressive responses without permanent ragdolls.)  

# Ownership and Attachments

**State Diagram:** Every interactive object has a simple state machine. Initially, props are *static* (instanced) and have no dynamic body. On collision or player action, they transition to *dynamic* with a physics body (and maybe joint connections). If an object is being held or carried by the player/NPC, mark it “owned” (so it persists across chunk unloads). When in range again and settled (no forces, velocity≈0, player far), return it to *static* or reset state (drop physics). A detached object never re-injects into an instanced mesh; instead, when “reset” it simply returns to the original static transform or is regenerated by the procedural system.  
(Detaching example: A cup on a chair is static until hit. On hit, it enters *dynamic*, with its rigid body and may spawn with random orientation. Later it sleeps and can either stick around or vanish on reset.) 

**Attachment Rules:** Use parent-child logic for attachments:
- *Seated Person:* NPC has a `sitting` flag. When seated, their world position is driven by the chair (no physics on NPC). On chair shake, apply brief joint constraints or inertia transfer: e.g. throw the NPC back a bit (via animation). If fall is warranted, set `sitting=false` and treat NPC as ejected.
- *Held Items:* If NPC holds a drink, set `cup.userData.owner=NPC`. On impact above a threshold, clear owner, spawn physics body on the cup, and let it drop. (Alternatively, one could attach the cup with a fixed Rapier joint to the NPC’s hand, then break the joint on impact.)
- *Cooler Lid:* Model the lid as a rigid body connected by a hinge joint. It opens/closes normally, and collisions on the lid generate rotation via the joint. If the cooler is tossed hard, the lid will swing open or detach if the joint is forced beyond limits.
- *Cups in Cupholders:* Either treat as free physics objects gently constrained by gravity/invisible support. On jolt, they simply fall off.
- *Signs:* A tall sign could be two bodies (signpost + sign). Use a hinge at the base or a soft-body simulation for bending. On a collision, the sign falls or tilts realistically. After settling, you could “break” it to a fallen static model.

Rapier’s joint constraints allow flexible attachments (hinges, fixed joints). We propose using fixed joints for cups in holders (so they move with the parent until broken) and hinged joints for lids or swayable poles. When an attachment breaks, remove the joint and let the child go dynamic. Keep ownership flags so held/dynamic objects aren’t double-generated.

# Chunk Streaming and Reset Logic

Divide objects between **static-instanced** (default) and **dynamic** (activated). Track each by chunk. Use a hysteresis strategy on streaming: only unload/reset objects once the player is several chunks away (e.g. unload radius = 2, purge/reset radius = 4, analogously to). If a dynamic object (like a cup or displaced chair) is being carried or is near the player, keep it alive and re-parent it to the current chunk to avoid duplication on reload. Once the player moves far and the object is idle, it can be removed or reset. 

**Safe Reset Invariants:**  
- *Far and Unobserved:* If no player/NPC is near a displaced object for some time, you may delete it or snap it back to its original state.  
- *Spawn on Return:* When a chunk reloads, only regenerate static default objects; any surviving dynamic objects should override this (e.g. an NPC leaving with a cooler).  
- *Origin-Chuck Tether:* Mark objects with their original chunk ID. On unload, if still in range (or held), keep them. If truly abandoned, let them “descend” back to initial state (e.g. sink into ground or fade) before removal.  
- *No Duplicates:* On reload, check if the dynamic instance exists; if so, do not recreate the static copy.

This ensures following an object (cup held by player) survives unloading and reloading of its home chunk without duplicating, and that a calm campsite eventually returns to its pristine state once everybody leaves.

# Synchronization of Physics, Rendering, and Gameplay

Use Rapier’s fixed-step simulation separate from rendering. After each physics step, update either the instanced-mesh matrices (for any re-instanced objects) or individual Mesh transforms. The existing Three.js animation system drives NPCs until a physics event triggers a switch. E.g. when a person is knocked, transition their motion from animation to kinematic physics for a few frames, then back to animation state, copying transforms by keyframes or IK goals. For navigation collision data (if using a navmesh), treat dynamic objects as temporary obstacles: either regenerate navmesh in a region (expensive), or simpler, have NPC pathfinding check obstacles via raycasts against dynamic bodies. 

The key invariant is: **game logic must query the updated position of any moved object**. If the game uses a simpler “collision” rep (like a bounding box for a table), we must update or disable it when physics moves the table. In practice, keep two collision representations: static (for instanced) vs dynamic (from physics). When an object goes dynamic, remove it from static collision queries, and let physics bodies handle collisions. NPCs avoid dynamic bodies via physics callbacks.

# Variation and Complexity Control

We avoid explosion of complexity by limiting scope of physics. Only activate groups of nearby objects on interaction. Use randomness and parameterization for variety:
- Assign each cup/chair/prop slight random mass, friction, or joint strength so collisions produce a range of outcomes.  
- Use rule-based event caps: e.g., one impact triggers at most one cup drop or chair tip per object (queue further reactions with cooldowns). This prevents runaway cascades (breaking a sign does not spawn dozens of tiny fragments; instead switch to a broken sign model).  
- For NPCs, prepare a handful of reaction animations or poses, triggered contextually (e.g. facing directions, grabbing seat, stumbling, etc.), to break monotony.  
- Keep global deterministic seeds for physics if needed (per chunk simulation seed) so that repeated runs look consistent (unless overridden by player interaction).

# Implementation Plan

1. **Engine Setup:** Integrate Rapier WASM via import-map (e.g. `@dimforge/rapier3d`). Ensure async loading works with no-build workflow. Test a simple world with falling cubes to confirm compatibility.  
2. **Static Instancing + Hit Detection:** Represent chairs, coolers, signs as InstancedMesh groups. Implement a raycast/collision test for player impact that identifies a specific instance (via InstancedMesh.raycast).  
3. **Activation Workflow:** On impact of an instanced object, remove that instance (using `count` trick) and create a new Mesh clone at that transform. Add a Rapier rigid body. Verify that the new object behaves physically (slides, tumbles).  
4. **Attachment Mechanics:** Implement hinged joint for cooler lid. Place a cup on a chair with a simple constraint (e.g. fixed position in chair local space). On chair collision, break the cup free (remove parent, add physics body), test cup drops realistically.  
5. **NPC Reaction Logic:** Give NPCs a physics capsule. On player collision at low speed, smoothly move the capsule and blend an idle animation. On high-speed hit, quickly blend to a “stumble” or “ragdoll” state, then back. Verify NPC doesn’t remain out of control.  
6. **Streaming/Reset:** Create a test “chunk” loader: when the player moves beyond radius, unload objects. Implement the unload/sleep logic from. Test carrying an object across a chunk boundary: it should not vanish. Also test leaving area: after delay, dynamic objects reset to original positions.  
7. **Navigation Sync:** If using navmesh, test that an object (e.g. a chair) moving doesn’t confuse pathfinding. If issues arise, fallback to simple raycast obstacles or ignore small props for nav.  
8. **Edge Cases:** Simulate stress: multiple quick collisions, chains (knocking one chair into another into cooler), and verify system stability (no memory leaks, objects eventually sleep and can be reset).  

Each milestone should have clear pass/fail:
- E.g. *“Chair + person collision”: pass if person returns to upright or seat after animation; fail if person clips through ground or chair remains unresponsive.*
- *“Chunk unload test”: pass if carried object isn’t duplicated; fail if static instance reappears or object disappears prematurely.*

# Conclusions

A hybrid design gives rich interactions without overshooting cost. Static instancing retains rendering speed, while Rapier-driven bodies handle physics where it matters. Objects revert once irrelevant, keeping memory low. NPCs remain mostly animated for control, with brief physics bursts for impact. This balances believability and performance.

**Strongest argument against overengineering:** Each additional physics detail (full ragdolls, soft-body signs, etc.) multiplies cost on low-end devices. Many interactions can be *faked* by clever animations or state changes: e.g. a “bent sign” model swap rather than true soft-body. Chaining physics effects risks blow-up (tumbles triggering more tumbles), so a simpler, rule-limited approach suffices. We avoid trying to simulate every domino: instead, design small believable set pieces (a knocked-over chair, a spilled cooler with a few cups) and let the emergent result appear playful but not physically perfect. This keeps the feature light and predictable on mobile devices, aligning with the gallery/game’s arcade style.

(Checks our animation-vs-physics blending.)

Observe whether the chair and cooler move, the cup dislodges, and the NPC (if any) falls appropriately. *Pass* if all expected events happen (chair moves realistically, cooler tilts, cup drops, NPC stumbles) and no object clips; *Fail* if something passes through another or stays incorrectly. (Tests chain reactions and constraint breaks.)

Each experiment’s outcome will guide final architecture tweaks.
