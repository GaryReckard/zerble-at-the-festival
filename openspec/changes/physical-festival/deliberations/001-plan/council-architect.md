## Architect's Position

### Priority Sequence

1. **Specify the production frame contract before implementing the fixed-step adapter.** The plan correctly retains cart and population ownership, but its fixed-step, publication and contact requirements do not yet name the barriers where those responsibilities meet. Add this to Task 2.2 (Fixed-step clock) and Task 2.5 (Cart proxy and resets), using the current order in `src/main.js:1177`, `src/main.js:1352-1363` and `src/main.js:1669-1709`.
2. **Resolve occupied resource adoption before completing render adoption.** Task 3.3 (Registry synchronization), Task 3.5 (World-owner adapters) and Task 5.1 (Reaction activity boundary) need one agreed seat-resource transfer contract. Existing reservations reference the campsite entry and exact slot, while furniture has a separate child collider (`src/campRegistry.js:104-118`; `src/people/campResources.js:15-35`). A moving collider alone cannot preserve a sitter's claim.
3. **Complete the bounded ownership ledger before broad content enrollment.** Include original-owner suppression manifests and dormant logical records in the capacity and eviction policy already required by design Decisions 1, 2 and 5 (`design.md:19-35`, `design.md:57-59`). Then retain the current progression through the occupied-chair production proof, cooler, cups and signs (`tasks.md`, Groups 6–9).
4. **Define sign validation independently of destination residency.** Retain the pure planner, but specify who supplies and invalidates built-access evidence before Task 9.2 (Pure sign intent planner) and Task 9.3 (Next-hop and built-target truth). The plan requires both order-invariant output and rejection of omitted destinations (`design.md:93-99`; `specs/festival-wayfinding/spec.md`, Deterministic useful placement and Truthful route and destination).

### Structural Risks Identified

- **The fixed-step integration has an unresolved ordering cycle.** The cart advances at `src/main.js:1177`, vehicles publish before the spatial-index barrier at `src/main.js:1352-1358`, adults run immediately afterward at `src/main.js:1361`, and world streaming, same-frame star activation and legacy collision correction occur later at `src/main.js:1669-1709`. Consequently, simply inserting the new solver before crowd steering can use a cart pose that a later wall collision corrects and can precede a star pickup that currently enables ghosting in that same frame. Inserting it at the old collision barrier instead leaves crowd steering and seated display using older prop poses. These are concrete integration choices, not reasons to replace the main loop. **Required refinement:** add an ordered frame table covering cart trajectory sampling, authoritative nonphysical collision correction, current ghost eligibility, solver substeps, reaction acquisition, registry/socket publication, existing adult/collection barriers, event scoring and render interpolation. Identify any deliberately one-frame-delayed feedback. Define which pose is authoritative for queries versus interpolated for display, including zero-substep frames at 120Hz and multiple-substep frames at 30Hz. Publish moving footprints and sockets during motion, not only at settlement as the wording at `design.md:51` currently suggests. **Acceptance:** extend the existing people trace with a chair crossing a spatial cell, a wall-plus-chair contact, same-frame star pickup and 0/1/multiple substep cases; demonstrate no double response, stale seat publication or accidental reordering of collection/scoring.

- **An occupied chair is presently a campsite resource, not an independently movable resource.** `src/campRegistry.js:104-106` puts `campSeats` on the campsite entry, while lines 107–118 create separate child collider entries and link them to slots. `campSlotValid` requires the exact original entry to remain registered and contain the exact slot (`src/people/campResources.js:27-35`). Removing/re-adding the chair collider or retaining its geometry therefore does not keep an occupied seat valid when the campsite unloads. The plan recognizes rebinding in general (`design.md:23`), but does not select the resource transition that the existing claim protocol requires. **Required refinement:** define whether support adoption transactionally rehomes the seat resource through the camp adapter or transfers the occupant into a reaction-owned support claim before the campsite disappears. Keep the population as person lifetime owner and use synchronous claim preparation and rollback, as required by `openspec/changes/people-npc-architecture/extension-guide.md`, “What an activity needs,” steps 3 and 6. Do not keep an entire campsite alive merely to preserve the old entry. **Acceptance:** add origin unload while the sitter is still supported, including two loveseat sitters, camp-music ownership, failed destination acquisition and a late old-owner release. Verify independent loads, valid replacement claims and harmless stale releases. This sharpens existing streaming tests rather than requiring a new universal resource graph.

- **Duplicate suppression can become an unbounded second persistence store.** The proposed original-owner manifests suppress regeneration (`design.md:23`), while visit records alone have an explicit eviction rule (`design.md:57`). Dormant records retain logical identity without bodies (`design.md:33`). If origin manifests retain keys after visit eviction, long travel can grow metadata indefinitely or permanently suppress a prop whose state no longer exists. **Required refinement:** make origin suppression, dormant enrollment and retained visit state part of one capacity-accounted ownership policy. An adopted live object must keep its suppression record; an eligible visit eviction must remove its matching suppression record coherently. Unchanged dormant props should be reconstructible from deterministic descriptors rather than requiring a permanent per-visited-prop record. **Acceptance:** augment Task 3.6 (Visit state and frontier) and Task 3.7 (Lifecycle stress gate) with long travel across many origins, forced eviction and revisit, asserting bounded metadata counts as well as bodies/render slots. This follows the existing bounded-state requirement in `specs/physical-props/spec.md`, rather than expanding persistence scope.

- **Sign truth needs a separate validation lifetime from streaming lifetime.** The design correctly forbids rendering/registry dependencies in pure worldgen and rejects omitted destinations (`design.md:93-97`), but a missing registry entry can mean a destination is merely unloaded: chunks and lakes have independent unload rules (`ARCHITECTURE.md:174-199`). Using currently registered destinations as truth would make signs depend on exploration order, contrary to the wayfinding delta's “Different exploration order” scenario. **Required refinement:** define validation evidence with stable destination/epoch identity and explicit unknown, accepted and rejected states. Assign the world-placement adapter responsibility for supplying evidence; absence due to unload must not become rejection. Pure sign intent stays deterministic, while runtime blade publication consumes validated evidence. Specify how an initially unknown target becomes validated and how genuine placement/access rejection invalidates a blade without changing unrelated signs. **Acceptance:** add destination-first versus sign-first loading, destination unload/reload and actual placement rejection to Task 9.3 (Next-hop and built-target truth). A deterministic placement/access proof can avoid retaining live destination objects; the plan need not introduce global routing.

The proposed module direction is otherwise sound: models expose geometry and local sockets, the physical owner owns simulation and adoption, existing population capabilities own people, and pure planning remains outside Three.js (`design.md:19-27`, `design.md:47-49`, `design.md:63`, `design.md:93`). Keep these as actual import boundaries in implementation rather than distributing engine handles into builders or activities. The plan already covers shared-resource disposal, lake ownership, seeded streams, a production-backed fixture and full-game acceptance (`design.md:49`, `design.md:55`, `design.md:111-115`; `verification.md`, Verification ladder).

Use the current Vite contract. `.claude/rules/no-build.md:3-5` records the approved migration, and its Module maintenance section explicitly forbids HTML module inventories. The briefing and current AGENTS.md correctly supersede the stale no-build/importmap instructions in the council/config templates. The new fixture belongs in Vite's entry configuration, as Task 1.3 (Production fixture shell) already specifies.

### Verdict

- **Verdict**: Proceed with mitigations
- **Key Concern**: The plan needs an explicit production frame/publication contract before the fixed-step solver can safely coexist with current cart correction, people barriers and same-frame ghost activation.
- **Recommendation**: Incorporate the four refinements into the existing design, tasks and negative scenarios, then proceed with the current staged implementation. No runtime rewrite, universal attachment framework or additional engine dependency decision is needed during this planning turn. This is a source-backed architectural review; no runtime or performance acceptance was performed.
