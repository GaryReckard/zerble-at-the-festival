## Adversary's Position

TL/DR: Proceed with mitigations. The proposed ownership split is sound, but the plan needs an explicit frame schedule, a generation-clearance contract and a guaranteed path for unavoidable releases under capacity pressure before implementation begins.

### Priority Sequence

1. Specify the solver's exact place in the production frame before Task 2.2 (Fixed-step clock) and Task 2.5 (Cart proxy and resets). The existing spatial, people, streaming and star-power barriers make this an integration decision, not an adapter detail (`src/main.js:1177`, `src/main.js:1355`, `src/main.js:1673`, `src/main.js:1679`).
2. Separate procedural placement evidence from displaced runtime footprints before Task 3.3 (Registry synchronization). Existing generation consults live registry clearance, so unchanged RNG alone cannot guarantee unchanged generated content (`src/chunks.js:1187`, `src/forests.js:907`, `src/registry.js:64`).
3. Reserve capacity for mandatory support loss and define occupied-seat adoption before Task 5.2 (Supported load and bracing). The current plan protects active objects but leaves forced release at saturation unresolved (`design.md`, decisions 2, 6 and 8; `src/people/campResources.js:27`).
4. Add the specific adversarial cases below to the production-backed fixture and real-campsite gate. Retain the current independent iOS, Low-tier and process-cleanup acceptance; these are correctly explicit already (`verification.md`, verification ladder and harness ownership; `src/threeShim.js:46`; `src/sound.js:271`).

### Vulnerabilities Found

- **Fixed stepping does not yet define accepted motion or publication order.** Severity: High. `design.md`, decisions 2, 3 and 6, require fixed stepping, accepted cart motion and publication through the existing people schedule, but do not say how these coexist. The cart currently moves once per accepted frame (`src/main.js:1177`), registry indexing precedes adult updates (`src/main.js:1355–1361`), streaming occurs later (`src/main.js:1673`), and star pickup deliberately precedes contacts so ghost mode engages on that same frame (`src/main.js:1676–1686`). Legacy contacts can still change cart position and speed at the end (`src/collisionContacts.js:36–60`). A solver inserted before adults can miss same-frame ghost activation and subsequent cart corrections; a solver inserted after contacts must republish affected bodies and indexes without rerunning ordinary activities. At 120 Hz some presentation frames have no physics step, while at 30 Hz one accepted cart endpoint can span multiple steps. Reusing that endpoint for each substep can distort proxy velocity even though the accumulator itself is correct.

  **Required refinement:** Add a frame sequence specifying cart endpoint sampling/interpolation, zero-step frames, ghost-filter sampling, legacy correction reconciliation, physics event draining, claim changes, spatial/socket publication and final visual interpolation. Distinguish authoritative solved state from interpolated display state, especially for attached sitters and cups. State which effects are deliberately deferred one frame. Add a same-frame star pickup plus chair contact, a legacy wall correction beside a physical chair, and 30/60/120 Hz replay with identical accepted input. Put this contract into Task 2.2 (Fixed-step clock), Task 2.5 (Cart proxy and resets), Task 4.2 (Single response owner) and the harness capability delta, without inventing a second people scheduler. The existing frame-dependency contract is in `ARCHITECTURE.md`, “Frame dependencies and accepted clocks.”

- **New or displaced registry footprints can alter generation without touching RNG implementation.** Severity: High. `design.md`, decision 11, promises preserved existing generation goldens, while decision 4 publishes displaced footprints into the live registry. The registry explicitly supports same-pass worldgen guards (`src/registry.js:64–68`). Shrub generation rejects a candidate through `closestBuilding` before calling `buildShrub(rng)` (`src/chunks.js:1187–1188`), and forest and lake trees also query live clearance (`src/forests.js:907`, `src/lakes.js:746`). Consequently, an adopted prop moved into a newly generated region, or a new sign registered before another builder runs, can change accepted content and downstream random consumption. A fresh sign salt does not prevent that coupling.

  **Required refinement:** Record a deliberate policy for procedural clearance versus live avoidance. Prefer preserving the old canonical placement blockers for generation and treating moving props/new decoration through a separate runtime-conflict policy, without changing current blockers as incidental cleanup. Define how a preexisting displaced prop and newly loaded canonical solid reconcile safely. Add a fixture comparing original-content descriptors and RNG results with identical seed/load order but different prop displacement and sign-install timing. Test exploration order separately against its established baseline rather than claiming the entire existing world is already order-independent. Extend Task 3.3 (Registry synchronization), Task 3.5 (World-owner adapters) and Task 9.2 (Pure sign intent planner).

- **Capacity rollback is insufficient when support must disappear.** Severity: High. Decision 8 in `design.md` says allocation failure preserves the original cup state, but decision 6 and the physical-person capability explicitly require a trapped sitter to release into falling when the chair loses support. The drink capability also requires holder release when its support threshold is exceeded. A saturated pool cannot keep a cup validly attached to a destroyed support, or keep a person seated on an airborne overturned chair, merely by rolling back a requested transfer. Decisions 2 and 5 protect active/support-critical records from eviction, leaving no guaranteed slot when all retained objects are protected.

  **Required refinement:** Separate optional transfers from mandatory releases. Reserve a bounded release allowance when admitting occupied chairs and supported/held cups, or define an equally bounded fallback representation that remains valid after source removal. Count that liability against the explicit provisional limits in Task 2.4 (Admission and residency), rather than waiting for final device limits. Test a fully saturated protected pool followed by both loveseat occupants falling, a holder breaking support and a person despawning with a held drink. Assert one representation, released claims, finite motion and no cap violation. These are consequences of existing accepted requirements, not additional optional content (`specs/physical-person-reactions/spec.md`, “Occupied support and continuous release”; `specs/drink-props/spec.md`, “Exclusive hand and holder transfer” and “Physical support release”).

- **Occupied adoption must transfer the resource identity, not only the prop entry.** Severity: Medium. Decision 1 permits registry remove/re-add with consumers rebound, and decision 4 transfers active rendering, but the chair reservation is tied to the exact world entry and actual slot membership. `campSlotValid` checks both (`src/people/campResources.js:27–35`), while release uses the slot token's identity (`src/people/campResources.js:38–41`). Merely keeping the chair's collider alive does not preserve a sitter's reservation when the campsite entry disappears. A rebinding implementation that weakens these checks could also let an old release free the replacement occupant.

  **Required refinement:** Make Task 3.5 (World-owner adapters) specify the occupied-resource transfer operation, including entry/slot replacement, supported load, current activity token and rollback. Add a real occupied-loveseat test that adopts the furniture while its camp owner unloads, then delivers the old owner's release after a new valid claim exists. Both remaining occupancy and replacement-claim protection must survive. Preserve the current guards; `git blame` attributes them to Gary Reckard's `25d10611`, the people ownership refactor, rather than treating them as obstacles to remove.

- **Hidden ticking is not equivalent to a paused tab.** Severity: Medium. Task 2.2 (Fixed-step clock) and the time acceptance row cover a long background pause and resume, but the actual scheduler continues calling `tick` through `setTimeout(16)` while hidden (`src/main.js:1820–1825`). An implementation that freezes only physics on `document.hidden` would let the existing cart/people schedule advance against frozen props, while a new RAF-owned solver would silently stop in the preview path. The accepted gameplay clock already clamps delta and gates frames (`src/main.js:1118–1119`), and Passport pause returns before gameplay (`src/main.js:1132–1136`).

  **Required refinement:** Drive physics from the same accepted gameplay frame and distinguish continuously ticking hidden execution, genuinely suspended execution with a long clock gap, Passport pause, and capture/input locks. Add separate cases for each; do not change the global scheduler in this feature. The fallback is an explicit historical behavior, attributed by `git blame` to Gary Reckard's `7c91d6d9` and `fe7e6f04`. Any future background scheduling overhaul needs its own acceptance, as also recorded in `.claude/rules/performance.md`, the October 8 audit's scheduling item.

### Verdict

- **Verdict**: Proceed with mitigations.
- **Key Concern**: The proposed fixed-step simulation has no explicit integration contract for the existing accepted-frame and contact barriers.
- **Recommendation**: Integrate these refinements into the design, ordered tasks and negative acceptance scenarios before runtime work. Keep the proposed production-backed chair-first rollout, bounded ownership, real-game boot and device gates. Do not add a second physics candidate, broaden to full ragdolls or restore obsolete importmap maintenance to resolve these issues. This review is source-based planning analysis; no runtime or performance acceptance was executed or claimed.
