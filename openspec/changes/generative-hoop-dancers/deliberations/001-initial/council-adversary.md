## Adversary's Position

### Priority Sequence

1. Specify a versioned, fully initialized pose sample and its publication order before adding motion primitives. The existing body write synchronously calls the renderer, so the session's sample must already represent the new time when it writes the person pose (src/crowd.js:2331-2341; src/people/hulaSession.js:44-47).
2. Prove both-hand forward kinematics against the actual arm shader and final body matrix, then prove one continuous contact phrase using those same production paths (src/personMotion.js:58-62,100-115; src/crowd.js:1730-1737).
3. Specify replay inputs and isolated composition separately from environmental eligibility. Test sampled output under two readers, frame partition changes, interruption, freeze, slot reuse and seek (design.md:23-25,41-45; src/people/runtime.js:44-60).
4. Implement single-person flow while retaining classic fixtures, and validate the real Low game path as well as the sandbox (src/threeShim.js:44-48; src/people/hulaActivity.js:33-35).
5. Add multi-hoop and partner ownership only after explicitly specifying all-or-none acquisition, reentrant cleanup and prop-capacity bounds (src/people/activityClaims.js:10-39,59-66).

### Vulnerabilities Found

These are identified design obligations, not claims that unimplemented flow code already fails.

- **A shared cached sample is insufficient without an explicit publication barrier.** Severity: High. Main runs adults before roaming (src/main.js:1361,1395), and HulaActivity advances HulaSession inside roaming (src/people/hulaActivity.js:35,49). During that advance, writeActivityPose immediately republishes the person and calls sampleBodyPose through _writeMatrices (src/crowd.js:2331-2341,2390-2398,1608-1609). If the flow cache is refreshed after the pose write, Crowd renders the previous score time while the hoop reads the next one. Entry, restart and finish can also publish during phase transitions (src/people/hulaSession.js:20-24,57,73-75). **Required mitigation:** advance score state and populate the complete cache before any synchronous person publication; specify an epoch/generation invalidation rule for phase/style changes and slot reuse. Test the actual production write path, not only two pure sampler readers.

- **Optional flow fields can survive in reused Crowd scratch storage and leak into classic dancers.** Severity: High. Crowd reuses one _activityBodyPose object for every participant (src/crowd.js:1609), while the classic sample overwrites only bob/lean/hoop fields (src/personMotion.js:64-66). The design proposes optional arm fields and absence-based classic fallback (design.md:39). Once a previous flow sample adds arm fields, classic output does not currently delete them, so an absence check is unsafe. **Required mitigation:** make every sample write an explicit style tag and all relevant fields, or branch on an explicit discriminator before reading flow fields. Do not use retained object properties as capability detection. Add a flow → classic → inactive → flow test in one reused output buffer across different people and after slot recycle.

- **A Low sandbox capture does not exercise Low's actual material replacement.** Severity: High. threeShim deliberately disables its Lambert swap for sandbox.html (src/threeShim.js:44-48), while hoop material code injects an emissive shader replacement (src/models/hulaHooper.js:53-58). The proposed workshop correctly uses the real rig, but that alone does not prove the live material path. **Required mitigation:** explicitly require a full-game Low compile/render check with the Lambert material type confirmed, plus Mid/High comparison, rather than accepting sandbox ?perf=low as material-tier evidence. Preserve the shim namespace rule and synchronous audio chain unchanged (src/threeShim.js:12-19; src/sound.js:271-335).

- **A seed and elapsed time cannot reproduce clearance-dependent composition without recording its environmental decisions.** Severity: Medium. The design both records a seed/profile/version/event timeline and rechecks dynamic obstruction at phrase boundaries (design.md:23,41). Current availability depends on registry object identity and current participant positions, not just elapsed time (src/people/hulaActivity.js:26-31,62-70). Replaying the seed in a different festival scene can reject a different candidate and diverge. **Required mitigation:** distinguish pure score replay from live encounter replay. Persist accepted phrase descriptors and the environmental decisions that affect branching, or persist deterministic fixtures for those inputs. Seeking in the workshop must not mutate real claims or rewind global cooldown clocks. Bound checkpoint/history storage and define bounded seek replay work.

- **Partner acquisition is not an existing transaction and can revoke unrelated activities before rollback.** Severity: High. ActivityClaims.acquire replaces an old claim after preparation rather than requiring the person to be unclaimed (src/people/activityClaims.js:24-29); Crowd's acquisition eligibility only excludes a short state list (src/crowd.js:2314). A naive two-call coordinator can steal the second person's claim and then fail, which cannot be undone by merely releasing the first. Cleanup callbacks can synchronously reenter ownership code (src/people/activityClaims.js:59-66). **Required mitigation:** establish non-stealing eligibility at the moment each claim is acquired, stage person/corridor reservations before publication, and revalidate both incarnations after acquisitions. Keep the coordinator inactive until all authority is current. Specify rollback and idempotent cross-partner cancellation, with tests where the second acquisition fails or releases the first synchronously. Reuse the established frisbee interruption principle rather than inventing a second people lifetime (ARCHITECTURE.md:858-866).

- **Resetting the score on safe return needs to preserve classic time and lifecycle semantics.** Severity: Medium. Current HulaSession preserves elapsed across interruption and returns through approaching (src/people/hulaSession.js:34-40,44-47,57). The new design deliberately requires a fresh reachable flow entrance (design.md:45), but does not yet separate total participation duration, phrase-local time and entrance time. Resetting elapsed globally would also alter classic behavior or extend flow indefinitely under repeated interruption. **Required mitigation:** retain classic elapsed exactly, define a separate flow score epoch and bounded active-participation timer, and explicitly decide how entrance time counts toward completion. Test multiple interruptions near the duration boundary, timeout, venue loss while paused and immediate person removal during reacquisition.

### Required Acceptance Additions

- Establish numerical contact and velocity tolerances before the first visual pass and test maximum supported scale/heading/lean combinations against both-hand shader parity (src/personMotion.js:58-62,100-115; design.md:29-35).
- Run boundary/publication tests at accepted deltas of zero and .05, including a phrase boundary followed immediately by finish or interruption; current runtime and sessions accept that range (src/people/runtime.js:44-48; src/people/hulaSession.js:29-31).
- Keep score progression frozen on rejected/debug-paused frames and NPC freeze, and never catch up from wall time after hidden-tab delay; main clamps and gates frames, while HulaActivity skips frozen NPC updates (src/main.js:1118-1119,1821-1825; src/people/hulaActivity.js:39; ARCHITECTURE.md:885-891).
- Assert post-disposal prop visibility, reservation release, buffer reset and repeat recreation, including a throwing cleanup callback so one failure cannot suppress other releases (src/people/hulaActivity.js:75-79; src/people/activityClaims.js:53-66).
- Preserve recent activity-transition handling and articulated locomotion when extending shared pose publication. Read-only history inspection found b5640af, 55e76ff, 3277b51 and 3e6d4af as the four latest changes touching these paths; this review does not propose reverting them (git log -4 -- src/people/hulaSession.js src/crowd.js, inspected 2026-10-29).

### Verdict

- **Verdict:** Proceed with mitigations.
- **Key Concern:** The proposed shared performance state must honor synchronous Crowd publication and reusable scratch storage, otherwise convincing pure sampler tests can coexist with visibly detached hands in the live game.
- **Recommendation:** Update the plan with the six obligations above, then proceed with the production-path workshop and one contact phrase. No current evidence requires a new rig, audio integration or worldgen changes; those should remain outside the initial proof. The partner stage needs its own explicit acquisition protocol before implementation.
