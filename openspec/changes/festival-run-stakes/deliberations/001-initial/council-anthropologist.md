## Anthropologist's Order of Operations

### Priority Sequence

1. **Title-card additions first, verified against the iOS audio tripwire before anything else.** Name input + mode selector are the very first thing every returning and new player touches, and they sit directly on the synchronous `Sound.init()` gesture (`src/main.js:648-651`). Tasks 1.1 and 1.5 already sequence "boot the main game + screenshot" right after the field lands — keep that order; don't let mode-selector styling or copy polish get ahead of the boot-clean check.
2. **Extend the `__dbg` harness for run-state before building the day-ramp logic**, not after. The day cycle is 6 minutes (`design.md` Context, citing `timeOfDay.js:19`); D6's table only gets interesting at Day 3-5+. Without a `__dbg` day-jump/vibe-nudge hook, verifying "does Day 5 actually feel harder" costs 15-30 real minutes of driving per iteration — a direct violation of the harness doctrine ("iterate, render, and verify in seconds, not minutes," `.claude/rules/sandbox-and-testing.md`). Task 6.8 lists `__dbg` drills for sputter and hits but not an explicit day/ramp-jump hook — add one before tuning starts, not as an afterthought once Q1's table is already "felt out."
3. **Build the persistent vibe-meter HUD contract before wiring the marshal-ladder logic underneath it.** Get the always-visible ambient feedback right first; the punishment math can follow once the widget exists to display it against.
4. **Local-board name-fallback and mode-default-selection UX pass before the Worker.** These are what the overwhelming majority of players will actually experience for the foreseeable future, since the global board ships feature-flagged off until Gary deploys (`design.md` D9 risk row, `-> Q4`). Getting the *local* experience right matters more than the Worker's polish right now.
5. **"Why did I die" clarity pass on the score screen**, verified via `__dbg.showScoreScreen(mock)` (task 2.3) across both death causes and at least two ToD presets, before declaring P2 done.
6. **Docs last** (task 7.1/7.2) — once behavior is locked, not before.

### Experience Concerns

- **End-User — the vibe meter has no ambient, continuously-visible state, unlike juice.** The `hud` delta spec (`specs/hud/spec.md`) explicitly gives the sputter grace a countdown ("the sputter grace countdown when active") but describes vibe feedback only as "vibe warnings at the marshal-ladder steps" — i.e., toast/whistle blips at threshold crossings (task 6.5: "warning whistle + toast"). The existing juice meter is always on screen (`index.html:145`, `$juiceMeter`), so a player always knows how close to trouble they are. The vibe meter, as specced, gives *no* signal between the warn and eject thresholds — a player takes a couple of stray hits, gets nothing, then suddenly a warning fires and they don't know how close eject actually is. That asymmetry (one stakes-death path is ambiently visible, the other is invisible until it isn't) reads as unfair rather than tense. Toasts are also transient by design (`hud.js:221`, default `ms = 1600`) — not the right vehicle for "how much runway do I have left."
- **End-User — mode default is unspecified and matters more than it looks.** Task 3.2 says "two mode buttons, persisted preselect" but neither `proposal.md` nor `design.md` states what a *first-time* player (no persisted preference) sees as the default/highlighted choice. Zerble today is a no-stakes, no-death sandbox — that's the entire established player expectation (README, title card tone). If Festival Run is the default-highlighted button, a returning player who taps Start out of habit gets ejected/dies in a game that has never done that before, with no warning that the rules changed. This isn't a hypothetical: it's the single biggest tone-continuity risk in the whole change, and it isn't a design decision anywhere in D1-D12.
- **End-User — local leaderboard has no stated name fallback for blanks.** The Worker guardrails explicitly promise "fallback display name for blanks" (`specs/leaderboard/spec.md`, Worker-side guardrails requirement) but the *local* top-10 requirement (`zerble-leaderboard-local`, task 2.1) makes no equivalent promise, and `player-identity`'s blank-name requirement only guarantees "no greeting, no name in copy" — it says nothing about what the score screen's board table shows in the name column when a player who never typed a name finishes a Festival Run (which is legal — name entry is optional per the spec, but Festival Run itself is not gated on having a name). Without a client-side fallback, the local board's first ten rows could read as a column of blank strings, which look broken.
- **Developer — no day-jump debug hook specced, but the tuning workflow depends on one.** Q1's answer ("proceeding with the draft table + `__dbg` overrides") implies overrides exist, but no task explicitly creates them, and task 6.8's playtest list (`setJuice(0)`, scripted hits, rescue path) doesn't mention a day-advance drill. Six months from now, whoever retunes D6's numbers (which Gary has already flagged as a placeholder — `design.md` "expected to move in playtesting") will either wait real minutes per iteration or reverse-engineer the missing hook themselves.
- **Developer — reusing "frown" for two jobs is a legibility risk for anyone reading the code cold.** `design.md` D8 states frowns "change jobs" between modes (dry-tank tax in the old code path vs. vibe-system feedback in Festival Run, `crowd.js` `onZerbleHit`). The mode-config gate (D2) keeps this behaviorally safe, but a maintainer six months out grepping for "frown" will find one code path serving two semantically different purposes depending on which mode object is active — worth a comment at the dispatch point (not per the "no comments unless the why is non-obvious" bar in CLAUDE.md, this genuinely qualifies) rather than relying on the reader to already know the history.
- **Cognitive Load — the stacking multiplier math (chain level x1-x4 times Lurleen's flat x2) is fine as designed, contingent on the single badge actually rendering both factors distinctly.** D12's ladder-index-from-chain-count and the "♥×2 slot" (task 4.4) sound legible on paper, but nothing in the plan calls for testing the badge's *readability at driving speed and camera distance* — the charter's own resolution rule #3 ("player delight wins when... effort stays proportional to what a player can perceive at driving speed and camera distance"). A HUD element that reads clearly in a static screenshot but not while steering with one thumb on mobile is a real, distinct failure mode from "the math is confusing" — worth a driving-speed screenshot check, not just the static combo-drill screenshots task 4.7 calls for.

### User Stories Not Addressed

- As a **returning player who has only ever known the no-stakes sandbox**, I would expect Start to still behave exactly as it always has, but the plan doesn't specify what mode is pre-selected for someone with no `localStorage` mode preference — if it defaults toward Festival Run, my first tap since the update could kill my cart with no warning that the game changed.
- As a **player approaching the vibe-meter's eject threshold**, I would expect some ambient sense of "I'm in danger" the way the juice meter always shows me my fuel, but the plan only gives me threshold-crossing toasts, so I'd be confused about why I suddenly got a warning (or got ejected) with no buildup I could see.
- As a **player who skipped the name field and still played a full Festival Run**, I would expect my result to show up cleanly on the local top-10 board, but the plan documents a fallback name only for the Worker's guardrails, not for the always-available local board — I might see a blank row and assume something broke.
- As the **next agent retuning the day-ramp table after Gary's first playtest** (design.md flags this as expected), I would expect a `__dbg` hook to jump straight to Day 5, but the plan doesn't task one, so I'd either wait out real 6-minute days or have to build the hook myself mid-task instead of it being ready.

### Verdict

- **Verdict**: Proceed with mitigations
- **Key Concern**: The vibe meter (one of two death paths) has no persistent, ambient HUD feedback comparable to the juice meter's always-visible state — the current spec only promises threshold-crossing toasts, which will make Festival Run's marshal-ejection death feel arbitrary and unfair rather than tense, undermining the whole "arcade stakes" goal the change is chasing.
- **Recommendation**: The plan is well-sequenced and the mode-config single-gate pattern (D2) is exactly the right shape for keeping Just Cruisin' invariant and legible to future maintainers. Before task group 6 starts, add: (1) an explicit default-mode decision (favor Just Cruisin' as the safe default, or an unmissable first-run choice screen — not a silent persisted-preference fallback) so the tone-continuity risk is closed by design rather than left to implementation accident; (2) a persistent vibe-meter widget spec'd alongside the sputter countdown, not just threshold toasts; (3) a local-board blank-name fallback matching the Worker's; and (4) a `__dbg` day-jump/ramp-override hook tasked explicitly (not assumed from Q1's answer) so the tuning loop stays in the seconds-not-minutes harness doctrine this project runs on.
